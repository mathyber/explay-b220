# Запуск J2ME-приложений

Цель — запускать с карты памяти обычные MIDlet-приложения (`.jar`) с правами,
которые им даёт MIDP: экран, клавиши, звук, хранилище, сеть. Доступа к флешу,
NV, звонкам и произвольной памяти у Java-кода нет — его ограничивает сама
Java-машина ([почему так](MEMORY_RU.md#что-это-значит-для-j2me)).

## Архитектура

```
E:\JAVA.GO1     — Java-машина, нативная программа GO1N (код + библиотеки, до 1 МиБ)
E:\JAVALIB.JAR  — библиотека классов (CLDC, MIDP, расширения Nokia)
E:\JAVA\*.jar   — MIDlet-приложения (список при запуске)
       │ загрузчик SD Apps: App Heap, перемещения, сообщения окна
       ▼
Java-машина в RAM ──► API загрузчика и функции прошивки (экран, файлы, таймеры, сеть)
```

* Во флеше места для машины нет (свободно 158 КБ кусками), поэтому она
  загружается с карты в Dynamic App Heap (1,4 МиБ одним блоком).
* Машина работает внутри окна SD Apps в задаче MMI и получает его сообщения.

## Этапы

| Этап | Содержание | Состояние |
|---|---|---|
| 1 | Нативные программы с карты (GO1N), исправление кучи, защита от перезагрузки при нехватке памяти | готово |
| 2 | API платформы для машины: вывод буфера RGB565 на экран, таймер и время, произвольный доступ к файлу (seek), нажатие и отпускание клавиш, запас стека задачи MMI | готово |
| 3 | Выбор Java-машины и сборка её на компьютере с заглушкой платформы; тесты CLDC | готово: своя GO1 JVM, на телефоне с JIT |
| 4 | Перенос машины в GO1N: «Hello» на Canvas, клавиши, перерисовка | готово: список игр из `E:\JAVA\`, консоль, MIDlet'ы |
| 5 | Один простой MIDlet: Canvas, Graphics, Image (PNG), Font, Display, жизненный цикл | готово; дальше настоящие игры: «Газила», Opera Mini 4.4, меню AoE III |
| 6 | RMS (файлы на карте), затем Connector (HTTP/сокеты через сеть прошивки), затем звук | RMS и Connector работают (2026-11-06), звука нет |

## Этап 1: что сделано

* Загрузчик SD Apps запускает программы `GO1N` ([SD_APPS_RU.md](SD_APPS_RU.md#нативные-программы-go1n)):
  до 1 МиБ, компоновка с базой 0, таблица перемещений, `.bss`, API в
  [patches/go1.h](patches/go1.h).
* Сборка C-программ — [tools/build_native_app.py](tools/build_native_app.py),
  с compiler-rt (деление, 64-битная арифметика, плавающая точка программно),
  что понадобится Java-машине.
* Все выделения памяти — App Heap с проверкой наибольшего свободного блока:
  нехватка памяти возвращает 0 вместо перезагрузки.

## Этап 2: что найдено и добавлено в API

| Возможность | Как устроено в прошивке | В API |
|---|---|---|
| Экран | Кадровый буфер всего экрана 176×220 RGB565 по `0x04280200` (литерал ROM `0x3aa01c`), строка 352 байта. `0x1d081f(dev, (x0<<16)\|y0, (x1<<16)\|y1)` объединяет прямоугольник с ожидающим обновлением (`0x4332f18`, флаг `0x4332f04`); после обработки сообщения прошивка отправляет его на LCD по DMA | `screen()`, `flush()` |
| Полная перерисовка | `0x4d67d3(2)` — PostUpdateScreenMsg, полное обновление; загрузчик вызывает его после выхода программы, чтобы восстановить полосу экранных клавиш | — |
| Таймер | MMK_CreateWinTimer `0x1f55ef(окно, мс, периодический)` → номер; MMK_StopTimer `0x1f5641`. Окно получает `0xf020`, параметр указывает на байт номера таймера | `timer()`, сообщение `GO1_TIMER` |
| Время | Системный счётчик `0x81003004`: 1 тик = 1 мс (его читает PS `0x484f88`) | `ms()` |
| Дата и время | RTC (`api->clock`, местное время от 1980-01-01) читается один раз при запуске машины, дальше время идёт только по `ms()`: значение не скачет, а игры двигают мир на разницу двух вызовов. `System.currentTimeMillis()` — местное время, зона по умолчанию GMT, как на телефонах тех лет. Перевод часов виден после перезапуска MIDlet | `clock()` |
| Файлы | SFS_SetFilePointer `0x5ee527(дескриптор, смещение старшее, младшее, начало)`; рядом SFS_GetFilePointer `0x5ee551`, SFS_FindFirstFile `0x5ee5c1`, SFS_FindNextFile `0x5ee8bb` | `seek()` |
| Клавиши | `0xfaKK` нажатие, `0xfbKK` отпускание, `0xfeKK` повтор, `0xfcKK` долгое, `0xfdKK` отпускание после долгого; коды в `go1.h` | все клавиши программе |
| Стек | Задача MMI: стек 10 000 байт (`0x408857c…0x408ac8b`, TCB ThreadX `0x42c5818`); на входе в обработчик SD Apps ниже SP ~9,6 КБ | — |

Проверено в эмуляторе на итоговой прошивке: градиент на весь экран и анимация
по таймеру (`apps/card_screen.c`), чтение с позиции 5 в `E:\APPS.LST`, счётчик
миллисекунд, коды всех клавиш при коротком и долгом нажатии, восстановление
экрана после выхода.

Ограничения:

* В эмуляторе таймер на 250 мс срабатывал примерно раз в 357 мс: виртуальное
  время эмулятора зависит от числа исполненных блоков, и перерисовка его тоже
  тратит. На телефоне точность и скорость нужно измерить.
* Java-машина должна держать кадры Java в куче, а не на стеке C, либо при входе
  переключаться на собственный стек в App Heap. Второе удобнее, но нужно убедиться,
  что в прошивке не включена проверка стека ThreadX.
* Поиск файлов (`FindFirst/FindNext`) найден, но формат структуры результата
  не разобран; для списка `.jar` пока можно читать файл-каталог.

## Этап 3: своя машина GO1 JVM

### Почему своя

| Вариант | Итог |
|---|---|
| phoneME Feature (Sun, GPLv2: CLDC HotSpot + MIDP 2.0 + javacall) | архив с 2017 года, сборка ломается даже на Linux (JDK 6, i686 GCC), C++; с библиотеками почти наверняка не помещается в 1 МиБ и 1,4 МБ RAM |
| SquirrelJME (MPL-2.0, движок NanoCoat на C) | стабильных версий нет, по словам автора «неполная»; требования к памяти и ОС не описаны |
| Своя компактная | под наши ограничения с самого начала: память из App Heap, без рекурсии на стеке C, big-endian, без ОС |

Источники: [SquirrelJME](https://github.com/SquirrelJME/SquirrelJME),
[архив phoneME](https://github.com/magicus/phoneME).

### Устройство

Исходники — [jvm/](jvm/): [jvm.h](jvm/jvm.h) (интерфейс), [class.c](jvm/class.c),
[heap.c](jvm/heap.c), [interp.c](jvm/interp.c), [native.c](jvm/native.c);
библиотека классов — [jvm/lib](jvm/lib).

* **Память.** Один блок от хоста: в начале метаданные классов и стеки потоков
  (выделяются подряд), остальное — куча объектов. Ссылки 32-битные, поэтому
  программа для Windows собирается под 32-битный x86.
* **Сборщик мусора.** Mark-sweep со свободными блоками first-fit; соседние
  сливаются. Поля объектов просматриваются точно по битовой карте ссылок класса,
  слоты стеков потоков — консервативно по карте начал объектов. Отметка идёт по
  явному стеку, с пересканированием кучи при переполнении. Когда памяти не
  хватает, куча уплотняется: живые объекты сдвигаются вниз, а объекты, на которые
  есть ссылки из кода на C, остаются на месте (подробнее — абзац «Память» ниже).
* **Интерпретатор.** Все инструкции, кроме `invokedynamic`: `jsr`/`ret` и
  `wide` старых компиляторов, `tableswitch`/`lookupswitch`, `multianewarray`.
  Кадры Java лежат в стеке потока внутри блока, вызов Java-метода не рекурсивен
  в C. Виртуальные вызовы через vtable, интерфейсные — через кэш на 256 записей.
  Инициализация классов: кадры `<clinit>` ставятся поверх текущего, инструкция
  повторяется после их возврата.
* **JIT.** На телефоне горячие методы переводятся в машинный код ARM
  ([jit.c](jvm/jit.c)), остальное и все трудные случаи остаются интерпретатору.
  Подробности — в [JVM_SPEED_RU.md](JVM_SPEED_RU.md#jit-2026-11-07).
* **Квант.** `jvm_run(budget)` выполняет не больше `budget` инструкций и
  возвращает управление; всё состояние лежит в блоке.
* **Потоки.** Лёгкие, планировщик внутри машины: по кругу, до 16 000 байткодов
  на поток за раз; при меньшем кванте Opera Mini ловит гонку между своими
  потоками. Есть `start`, `currentThread`, `join`, `sleep`, `yield`,
  `interrupt`; мониторы с повторным входом, `wait` (в том числе с таймаутом),
  `notify`/`notifyAll`. После `wait` поток заново захватывает монитор
  с прежним счётчиком входов.
* **Нативные методы** возвращают результат или просят интерпретатор либо
  продолжить после поставленного ими Java-кадра (`newInstance` вызывает
  конструктор), либо повторить вызов после `<clinit>` (`Class.forName`).
* **JAR.** [jar.c](jvm/jar.c): центральный каталог ZIP и свой inflate
  (RFC 1951: несжатые блоки, фиксированные и динамические коды Хаффмана).
  Архив читается через функцию «прочитать по смещению», поэтому в памяти
  держатся только каталог и извлекаемая запись. Ядро машины получает классы
  и ресурсы одинаково — через `host.read(путь)`; поиск в библиотеке и архиве
  делает платформа. `Class.getResourceAsStream` (абсолютные и относительные пути).
* **Без libc.** Своё `memcpy`/`memset`, точный `fmod` (по образцу musl),
  форматирование чисел; float и double на телефоне — программные из compiler-rt.
* **Библиотека** — свои `java.lang`/`java.io`/`java.util` по API CLDC 1.1:
  строки, обёртки чисел, `Math`, `Thread`, `Class.forName`/`newInstance`,
  `Vector`, `Stack`, `Hashtable`, `Random` (тот же генератор, что в JDK), `Date`,
  `Timer`/`TimerTask`; `java.io`: `InputStream`, `ByteArrayInput/OutputStream`,
  `DataInput/OutputStream`, `InputStreamReader`/`OutputStreamWriter` (UTF-8,
  ISO-8859-1), `Reader`/`Writer`; плюс `StringBuilder` для склейки строк. Собирается локальным JDK 25:
  `javac -source 8 -target 8 -bootclasspath <наша библиотека>`, формат классов 52.
  Принимаются классы версий 45–52, то есть и старые MIDlet.

### Проверка

```powershell
.\.venv\Scripts\python.exe -m tools.build_jvm
.\.venv\Scripts\python.exe -m unittest tests.test_jvm
```

Каждая программа из [jvm/tests](jvm/tests) компилируется дважды — против нашей
библиотеки и против JDK — и выполняется на обеих машинах; вывод должен совпасть
байт в байт. `Basics` покрывает арифметику и граничные случаи деления и сдвигов,
long/float/double и преобразования, строки, массивы, `switch`, исключения
с `finally`, наследование, интерфейсы, статическую инициализацию. `GcStress`
на куче 160 КБ проходит десятки сборок и сверяет выжившие объекты.
`Threads` проверяет передачу через `wait`/`notify`, `join`, прерывание сна,
общий счётчик под `synchronized` у трёх потоков, `wait` с таймаутом,
`Class.forName` с инициализацией, `newInstance`, `Timer`. `Collections` —
`Vector`, `Stack`, `Hashtable`, `Random(42)`. `Resources` запускается из
`.jar`, который тест собирает сам: сжатые и несжатые записи, текст UTF-8
с кириллицей, двоичные данные через `DataInputStream`, файл 200 КБ
с динамическими кодами Хаффмана, относительный и отсутствующий ресурс.

Программа для Windows: `go1jvm [-heap КБ] [-meta КБ] [-cp каталоги] [-jar архив] Класс`. Ядро машины
компилируется и под телефон (Thumb big-endian, без libc).

## Этап 4: Java на телефоне

[jvm/phone_main.c](jvm/phone_main.c) — машина как нативная программа `JAVA.GO1`
(43 КБ вместе с compiler-rt). Сборка и установка на карту итоговой прошивки:

```powershell
.\.venv\Scripts\python.exe -m tools.build_java_phone [--app apps/java/Hello.java]
```

Затем `Start B220 CUT.cmd` → главное меню → «Приложения» (правый нижний пункт) → Java.

* На карте: `JAVA.GO1`, `E:\JAVALIB.JAR` (библиотека, 59 КБ) и `E:\APP.JAR`
  (приложение, главный класс — `Main-Class` в манифесте).
* Память: один блок из App Heap — всё свободное, кроме 64 КБ запаса прошивке (подробнее — «Память» ниже);
  из него 256 КБ метаданных, остальное куча (около 1 МБ).
* Машина работает по разовому таймеру окна. Каждое срабатывание выполняет
  `jvm_run` порциями по 2000 байткодов до 30 мс по часам. Пока есть работа,
  следующий таймер ставится на 1 мс; если все потоки спят — до ближайшего
  пробуждения, но не дольше 20 мс. Время — счётчик миллисекунд прошивки.
  До 2026-11-06 было ровно 20 000 байткодов на периодический тик 20 мс. Это
  ограничивало машину и в эмуляторе, после перехода интерпретатора на ARM.
* Потоки: очередь по кругу, ход потока — до 16 000 байткодов, и он сохраняется
  между вызовами `jvm_run`. Поток, который уснул или ждёт, отдаёт ход сразу.
* Интерпретатор (`interp.c`), графика (`midp.c`), распаковка JAR (`jar.c`) и куча
  (`heap.c`) собраны в режиме ARM, остальное в Thumb.
* **Быстрые формы команд**, как в KVM. После первого выполнения команда
  заменяется в байткоде:
  - `getfield`/`putfield` получают в операнде готовое смещение поля;
  - `getstatic`/`putstatic` — указатель на поле без поиска, когда класс уже
    инициализирован;
  - `invokevirtual`/`invokespecial`/`invokestatic` — готовый метод, если он
    обычный (не native, не synchronized).

  Виртуальный вызов, у которого реальная цель оказалась native или
  synchronized, навсегда переходит на общий путь (`INVOKEVIRTUAL_SLOW`).
* Распаковка: канонический декодер Хаффмана с таблицей для кодов до 8 бит;
  более длинные коды читаются по битам.
* `serviceRepaints` ждёт, пока кадр нарисован (`wait/notify`), как требует MIDP.
  Раньше он возвращался, когда рисование только начиналось.
* `System.out` — консоль на экране, 9 последних строк по 28 символов,
  не-ASCII пока показывается как `?`. По окончании `[finished]`, OK — выход.
* Перед выгрузкой загрузчик присылает `GO1_CLOSE`: машина закрывает файлы
  и освобождает свой блок.

Проверено в эмуляторе на итоговой прошивке: [apps/java/Hello.java](apps/java/Hello.java)
выводит строки, `fib(15)`, `Vector`, `Math.PI`, результат второго потока, `sleep`
по часам телефона и свободную память. Быстрая проверка без эмулятора —
`tests.test_sd_app` (`test_java_vm_runs_a_program_from_jars`): `JAVA.GO1`
выполняется в Unicorn с подменёнными вызовами прошивки, файлы читаются частями
через `seek`, часы идут по 20 мс на сообщение таймера.

### На настоящем телефоне (2026-11-14)

Прошивка CUT записана в B220 (UpgradeDownload, PAC только с PS — `tools.build_pac`).

| Программа | Результат |
|---|---|
| BENCH.GO1 | работает: счёт 0,71 от эмулятора, копирование памяти 0,24, вызовы прошивки 0,87 |
| GAZila | работает, кадров мало |
| Opera Mini 4.2 / 4.4 | работает, страницы грузятся медленно (GPRS) |
| Age of Empires 3 | до самой игры не доходит |
| BROWSER.GO1 | работает, страницы грузит |

**Главная находка: ядро B220 — ARMv4T** (класс ARM7TDMI), а не ARM926. В PS нет
ни одной команды `blx` по регистру, `clz` или CP15, зато больше 9000 `bx`.
Эмулятор работал на ARM926 и прощал то, на чём телефон перезагружался:

- Деление с остатком из compiler-rt Zig (`__aeabi_{u,}{l,}divmod`) написано на
  ассемблере и возвращается `pop {pc}`. На ARMv4T такая загрузка в pc не
  возвращает в Thumb, и Thumb-вызывающий продолжал как ARM-код. GAZila падала в
  `Long.toString` (печать свободной памяти), браузер — на загрузке страниц.
  Исправление — [patches/aeabi_v4t.S](patches/aeabi_v4t.S) с возвратом `bx lr`;
  сборщик подключает его в каждую GO1N-программу.
- JIT вызывал помощников через `blx r12` и сбрасывал кэш командами `mcr p15`.
  Теперь `mov lr, pc; bx r12`, сброса кэша нет (`JVM_ARM926_CACHE` оставляет старый
  код для ARMv5).
- Быстрые тесты (`tests.test_sd_app`) теперь идут на ARMv4T-модели Unicorn
  TI925T. Без исправления на ней падают три теста Java.

Как искали: журнал `E:\JAVA.LOG` (сборка с `-DJVM_PHONE_LOG`: этапы запуска,
чтения из JAR, сборки мусора, PNG, долгие такты, свободное место в кучах
прошивки) показал точку падения. По дороге исключены JIT, сторожевой таймер
(BENCH держит процессор 3 с без перезагрузки), стек (у задачи `T_P_APP` 10000
байт, занято до 3568), невыровненный доступ и память: `MEMTEST.GO1`
([apps/card_memtest.c](apps/card_memtest.c)) 150 с держал 1,42 МБ App Heap без
единой ошибки. Варианты сборки задаются флагами `defines` в `build_vm`:
`JVM_NO_JIT`, `JVM_PHONE_LOG`, `JVM_NO_STATIC`, `RESERVE=…`, `YIELD_MS=…`.

## Этап 5: MIDP

Первый MIDlet — [apps/java/Bounce.java](apps/java/Bounce.java) (`GameCanvas`, поток
игрового цикла, опрос клавиш, текст по-русски) — работает в эмуляторе на итоговой
прошивке:


## Выбор игры

`JAVA.GO1` при запуске показывает список `.jar` из папки `E:\JAVA\` — имена
файлов любые, в том числе длинные и русские; список отсортирован по имени файла.

В строке — название игры из манифеста (`MIDlet-Name`, UTF-8, с переносами строк
манифеста) и её иконка 16×16 слева (`MIDlet-Icon`, иначе второе поле `MIDlet-1`).
Иконка больше 16 px уменьшается усреднением пикселей, меньшая ставится по центру.
Без названия показывается имя файла без `.jar`, без иконки место слева пустое.

* Для каждого JAR читаются только оглавление, манифест и PNG иконки (декодер тот
  же, что у `Image.createImage`, вызывается без запущенной машины). Иконки
  больше 256×256 не декодируются.
* Названия и иконки занимают около 1,4 КБ на игру и освобождаются перед запуском
  машины, после игры читаются заново: Java-куча ничего не теряет.
* Нужна прошивка, где у API есть `text_at` (текст с координатой X, с 2026-11-05);
  на более старой список остаётся прежним, по центру.

| Клавиша | Действие |
|---|---|
| вверх/вниз, 2/8 | выбор (по кругу, по 6 строк на страницу) |
| OK, левая экранная, 5 | запустить |
| правая экранная, красная | назад в SD Apps |

Когда MIDlet завершается (или после `[finished]` консольной программы нажат OK),
машина освобождает всю свою память и список появляется снова. Долгое нажатие
правой экранной во время игры, как и раньше, сразу возвращает в SD Apps.

**Отпускание клавиш.** Java-машина отдаёт программе отпускание клавиши только
после того, как программа нарисовала два кадра с момента нажатия (не дольше
500 мс). Меню Age of Empires III проверяет раз в кадр, зажата ли клавиша. В
эмуляторе кадр длится около 100 мс, и нажатие, которое целиком попадало между
двумя кадрами, терялось: курсор выбора языка двигался через раз.

**Память.** Один блок из App Heap. Куча растёт снизу, описания классов (байткод,
константы, таблицы) — сверху. Граница между ними подвижная:
- куча занимает неиспользованное у описаний, но только сколько нужно для текущего
  выделения плюс 64 КБ, и оставляет описаниям 16 КБ запаса;
- описания забирают свободный хвост кучи.

Начальная граница — оценка по размеру классов в JAR. Раньше оценка была
окончательной, а она часто ошибалась: Age of Empires III использовала 250–356 КБ
из 436, Opera Mini — больше оценки.

**Уплотнение кучи.** Когда выделение не удаётся даже после сборки мусора и займа
у описаний, и при `System.gc()`, живые объекты сдвигаются вниз и закрывают дыры.
Без этого память дробилась: у Age of Empires III в эмуляторе было свободно 317 КБ
в 399 кусках, самый большой 52 КБ, и загрузка падала с `OutOfMemoryError`.

Объекты, на которые ссылаются не точные ссылки, не двигаются:
- значения в слотах стеков Java и сами массивы стеков;
- поля `Thread` и `Frame`, мониторы, временные корни;
- слова на стеке C и в сохранённых регистрах, включая указатели внутрь массивов;
- объекты с флагом `FIXED`: состояние `JarStream` (указывает само на себя) и
  объекты, у которых взяли `hashCode`/`identityHashCode` (хеш — это адрес).

Точные ссылки исправляются:
- поля объектов и массивы ссылок;
- статические поля, объекты `Class`;
- строковые константы, таблица `intern`.

Каждый подвижный объект занимает самую нижнюю дыру, в которую помещается, даже
под закреплённым объектом; иначе съезжает вниз. Новые адреса хранятся как серии
соседних объектов с одинаковым сдвигом, в постоянной таблице (слово на 512 байт
кучи, около 9 КБ).

**Описания классов вне блока.** Когда своя область кончилась, куски по 16 КБ
берутся в таком порядке:
1. Static Byte Heap (`api->alloc_static`);
2. свободные куски App Heap, которые не занял блок Java-машины;
3. хвост кучи;
4. закреплённый `byte[]` внутри кучи.

В обеих кучах прошивке всегда остаётся по 64 КБ. Задний буфер экрана (77 КБ)
тоже лежит в Static Byte Heap.

**Прозрачность картинок.** У неизменяемых картинок, где прозрачность только
0 или 255, — бит на пиксель вместо байта. PNG распаковывается построчно (поток
распаковки и две строки, а не вся картинка сразу), прозрачность пишется сразу
в биты. Первое промежуточное значение переводит картинку на байты, и готовые
строки переносятся. Рисунок совпадает с байтовым бит в бит (`AlphaTest`,
`PngTest`).

**Предел памяти.** Кампании Age of Empires III нужно около 1,7 МБ кучи и 0,5 МБ
описаний классов: на ПК она не помещается даже в 1,4 МБ. У B220 Java-машине
достаётся около 1,2 МБ плюс ~150 КБ из других куч. Меню, настройки и выбор
кампании работают, сама кампания — нет.

Проверка: `GO1JVM_COMPACT=1` на ПК уплотняет после каждой сборки мусора. Под ним
проходят все тесты Java-машины, старт Opera Mini и поездка в «Газиле».

**Двойная буферизация.** MIDlet рисует в собственный задний буфер (77 КБ из памяти
программ). `flush` копирует готовый прямоугольник в экранный буфер окна и только
потом просит прошивку обновить экран. Прошивка передаёт экранный буфер на LCD
позже, поэтому при рисовании прямо в него было видно недорисованные кадры.
Например, Age of Empires III непрерывно перерисовывает меню выбора языка,
и кнопки «мигали».

**Красная кнопка** во время MIDlet ведёт себя как на телефонах того времени:
1. MIDlet получает `destroyApp(true)` и может сохранить данные.
2. Машина останавливается, даже если у программы остались живые потоки (у Opera Mini они есть).
3. Список появляется снова.

Если `destroyApp` не вернулась за 3 секунды или красную нажали ещё раз, программа
закрывается сразу. В консольной программе и после ошибки красная закрывает её
сразу, в списке — выходит из Java-машины. Тесты `RedKey` и `RedKeyStuck`
в `tests.test_sd_app`.
Если в `E:\JAVA\` нет ни одного `.jar`, запускается `E:\APP.JAR` (как раньше),
а без него показывается подсказка, куда класть файлы.

Установка в образ карты эмулятора — `--jar` можно повторять:

```powershell
.\.venv\Scripts\python.exe -m tools.build_java_phone --jar игра1.jar --jar игра2.jar
```

На настоящую карту: `JAVA.GO1`, `JAVALIB.JAR` и `APPS.LST` (строка `JAVA.GO1`)
в корень, игры — в папку `JAVA`. Для этого загрузчику понадобились поиск файлов,
открытие по пути UCS-2 и текст UCS-2 (см. [SD_APPS_RU.md](SD_APPS_RU.md));
прошивку нужно пересобрать. Генератор образа карты ([tools/sd_image.py](tools/sd_image.py))
теперь умеет папку с длинными именами (LFN) — так проверены и тесты, и поиск
прошивки в эмуляторе.

### Что изменено в машине ради памяти

Метаданные Opera Mini 4.4: было 738 КБ, стало ~535 КБ.

* **Классы.** От файла класса остаются только строки и байткод; служебные
  атрибуты (`StackMap`, номера строк) не хранятся. Файл освобождается до
  компоновки, а значит, до загрузки суперкласса.
* **Константы** — 8 байт вместо 12: индексы ссылок живут в том же поле, куда
  потом пишется разрешённый указатель.
* **Стеки потоков** — массивы `int[]` в куче: сначала 1 КБ, удваиваются до 32 КБ
  при нехватке, указатели кадров переносятся. Было по 16 КБ метаданных на поток.
* **Мониторы** освобождаются при последнем выходе, а не при сборке мусора
  (Опера синхронизируется на сотнях объектов; таблица на 64 переполнялась).
* **Ресурсы больше 40 КБ** читаются потоком: распаковка по мере чтения с окном
  32 КБ (`go1.ResourceStream`, `jar_stream_*` в [jar.c](jvm/jar.c)). Ресурс `a`
  Оперы 7.0 весит 292 КБ, теперь он не лежит в куче целиком.
* **Распаковка из JAR** читает сжатые данные кусками по 256 байт, без буфера на
  всю запись. На телефоне распакованный файл класса кладётся во временный
  массив в куче машины (`jvm_scratch_alloc`): снаружи остаются только 64 КБ
  запаса, а класс Оперы 7.0 весит 283 КБ.
* **Размещение в куче.** Объекты берутся от начала самого нижнего свободного
  блока, временные буферы — с самого верха. Раньше Опера 4.4 падала при куче
  740 КБ, когда живых объектов было 181 КБ, а самый большой свободный кусок —
  66 КБ; теперь ей хватает 600 КБ.
* **Мёртвые локальные переменные.** Opera Mini 7.0 проверяет память, заполняя
  `Vector` блоками по 8 КБ до `OutOfMemoryError`, и оставляет его в локальной
  переменной. Сборщик теперь для вызывающих кадров проверяет по байткоду,
  будет ли переменная прочитана дальше (переходы и обработчики исключений
  учитываются; методы с `jsr`/`ret` и верхний кадр — по-прежнему целиком).
  Старые значения выше вершины стека больше не считаются корнями.
* **Раскладка памяти на телефоне** зависит от приложения: метаданные =
  176 КБ + 1,4 × размер его классов, остальное — куча (раньше было 512 КБ на всё).

Диагностика в сборке для Windows: `GO1JVM_STATS=1` печатает кучу, пик живых
объектов, самый большой свободный блок и разбивку метаданных; `GO1JVM_HEAP=1` —
живые объекты по классам. Сообщение `OutOfMemoryError` от `newarray` содержит
тип и длину массива, а непойманное исключение — цепочку методов.
