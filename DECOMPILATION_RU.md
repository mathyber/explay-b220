# Читаемый вид прошивки: Ghidra и C-подобный псевдокод

Подготовлен рабочий пилот анализа исходного PS B220 в **Ghidra 12.2**.
Из настоящих машинных инструкций получены псевдокод и ассемблер девяти функций.
Это начало размеченной базы для переработок; исходники производителя не восстановлены.
Исходная прошивка, экспериментальные PS и эмулятор этим анализом не изменяются.

## Что можно получить

- Дизассемблирование ARM/Thumb: реальные инструкции и адреса.
- C-подобное представление условий, циклов, вызовов, указателей и структур.
- Переходы по вызовам/ссылкам, графы потока управления, имена и комментарии.
- Постепенно уточняемые типы, сигнатуры и карту модулей.
- Отдельно — извлечение ресурсов в привычные форматы и их повторную упаковку.

Названия функций и параметров, комментарии, typedef и исходная файловая
структура обычно не сохраняются в raw PS. Их приходится устанавливать по
поведению, строкам диагностики, ABI и наблюдениям эмулятора. Оптимизированный
машинный код также не задаёт единственный исходный C-текст.

Поэтому результат декомпилятора нельзя считать проектом, который можно целиком
отредактировать, нажать Build и получить ту же прошивку. Псевдокод помогает понять
функцию и переписать её или подготовить точный патч. Для сборки целого аналога
понадобилось бы восстановить существенно больше типов, модулей и связей.

В проекте уже есть и настоящий редактируемый код: `patches/sd_app.c`,
`patches/catch_game.c` и наши ассемблерные вставки. Они компилируются отдельно
и встраиваются в PS. Для оригинальных функций используется иной процесс:
понять по Ghidra/трассам → написать замену → проверить её в отдельном образе.

## Открыть подготовленный проект

Дважды щёлкните **`Open B220 Ghidra.cmd`**. Переносимые зависимости уже загружены
в этой рабочей папке. Скрипт открывает проект и его единственную программу в GUI.
При первом запуске самой Ghidra могут появиться её стартовые диалоги.

В списке функций ищите префикс `b220_`, либо нажмите **G** и введите адрес.
Окно **Decompiler** показывает C-подобное представление; Listing — инструкции.
Наша разметка уже достаточна для этих функций. Полный Auto Analyze бинарника
пока не запускался: в нём много картинок, строк и таблиц, а код смешивает ARM
и Thumb. Для знакомства с готовым пилотом запускать полный анализ не требуется.

Файлы:

- `analysis/reverse/projects/B220-original-pilot.gpr` и соседний `.rep` — база Ghidra.
- `analysis/reverse/original/*.c` — настоящий вывод декомпилятора.
- `analysis/reverse/original/*.asm` — соответствующие инструкции.
- `analysis/reverse/original/index.tsv` — адреса, режимы и результаты.
- `analysis/reverse/manifest.json` — происхождение и параметры проекта.

Основные примеры:

| Функция | Адрес | Назначение |
|---|---|---|
| `b220_font_height` | `0x5B870C`, Thumb | Выбор высоты 14/16 по режиму шрифта |
| `b220_select_font_tables` | `0x5B862C`, Thumb | Выбор найденных таблиц шрифта |
| `b220_sfs_open` | `0x5EDC5E`, Thumb | Обёртка открытия файла |
| `b220_sfs_read` | `0x5EE49E`, Thumb | Обёртка чтения файла |
| `b220_sfs_size` | `0x5EE59E`, Thumb | Получение размера |
| `b220_sfs_close` | `0x5EE484`, Thumb | Закрытие файла |
| `b220_sokoban_launch_original` | `0x60EEE8`, Thumb | Исходный вход в Сокобан, до нашего перенаправления |
| `b220_sokoban_window_original` | `0x60F74E`, Thumb | Исходный обработчик игрового окна |
| `b220_rgb565_rle_row` | `0x527728`, ARM | Декодер растров, участвующий в выводе перекрашенного скроллбара |

Все описательные имена `b220_` назначены нами. Это не символы из утёкших исходников.
Функции с `b220_unanalyzed_` обозначают ещё не разобранных вызываемых соседей.
`undefined*`, предупреждения и не восстановленные переходы в C-файлах — места,
которые требуют дополнительной разметки, а не готовые решения для переноса в C.

## Как подготовлен пилот

Вход — исходный PS, SHA-256:
`7bd1dd7b3ce3a3efa65f957eb24e4e4b3114775c8b7770121f98b39816bacbeb`.
База raw binary — 0, язык **ARM:BE:32:v4t**, компиляторная модель `default`.
Это рабочая модель для исследованных инструкций; исходный компилятор/SDK
производителя этим выбором не устанавливается.

Добавлены RAM `0x04000000…0x043FFFFF` и SRAM `0x40000000…0x4000FFFF`.
В них перенесены два начальных диапазона данных из установленной таблицы старта:
`0x7237CC → 0x04293600`, размер `0x2001C`, и
`0x74432C → 0x40003400`, размер `0x364`.
Это начальное статическое представление, а не состояние загруженного телефона.
MMIO, DSP, все алиасы памяти и весь граф выполнения этим пилотом не размечены.

Для девяти функций заданы ограниченные диапазоны и режим ARM/Thumb. Установлены
известные имена аргументов, нулевой сдвиг стека при вызовах и несколько меток
данных. Эпилоги `POP {R3}; BX R3`, восстанавливающие сохранённый LR, помечены
как возвраты. Без этой разметки Ghidra в пилоте ошибочно показывала часть
возвратов как не восстановленные таблицы переходов. Бинарные инструкции не менялись.

## Воспроизведение

```powershell
.\.venv\Scripts\python.exe -B -m tools.setup_reverse_tools
.\.venv\Scripts\python.exe -B -m tools.prepare_reverse_project
```

При существующем проекте обычная команда сохраняет ручные аннотации.
`--rebuild` заново импортирует программу и заменяет аннотации этого пилота.
Закройте GUI перед явной пересборкой базы.

Скрипты: [установка](tools/setup_reverse_tools.py),
[подготовка](tools/prepare_reverse_project.py),
[разметка и экспорт](tools/ghidra/B220Pilot.java).

Используются официальные ZIP:
[Ghidra 12.2](https://github.com/NationalSecurityAgency/ghidra/releases/tag/Ghidra_12.2_build)
и [Temurin JDK 25.0.5+8](https://github.com/adoptium/temurin25-binaries/releases/tag/jdk-25.0.5%2B8).
[Инструкция Ghidra](https://github.com/NationalSecurityAgency/ghidra/blob/Ghidra_12.2_build/README.md)
требует JDK 25. Версии и SHA-256 закреплены в установщике; архивы проверяются
перед распаковкой. JDK нужен для инструмента анализа на ПК.

Архивы, распаковки, настройки, кеши и база анализа остаются под `analysis/`,
вне Git. PATH, системная Java и настройки других приложений не меняются:
пути Java/профиля переопределены только для дочерних процессов Ghidra.

Следующий полезный этап — расширять размеченную базу по конкретным задачам:
оформление и ресурсы, пункты меню и их зависимости, файловые службы. Так можно
отделять собственный код удаляемого модуля от общих функций, нужных остальной системе.
