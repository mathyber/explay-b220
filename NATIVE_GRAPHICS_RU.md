# Нативный вывод B220 MOD

**Новый образ выводит `B220 MOD` штатным шрифтом прошивки.** Наша Thumb-вставка
перехватывает вызов рендерера заголовка «Время», меняет указатель строки
и её длину, затем передаёт управление исходной графической функции.
Результат проходит через гостевой framebuffer, DMA и LCD эмулятора.

![Кадр LCD после штатного рендерера](analysis/firmware-patches/ui-label/proof/visible-title.png)

## Запуск

Дважды щёлкните **`Start B220 MOD.cmd`**. Теперь этот запуск собирает расширенный
образ, в котором работают и [перехват клавиши с меткой](FIRST_PATCH_RU.md),
и вывод заголовка. Обычный `Start B220.cmd` выбирает оригинал.

На свежей экспериментальной NOR появляется настройка даты. Нажмите левую
экранную клавишу «Подтв.»: следующее окно настройки времени получит заголовок
**B220 MOD**. На уже настроенной NOR начальное окно может быть другим.
Рабочее состояние с надписью сохранено в локальном снимке
`analysis/firmware-patches/ui-label/proof/working-title.b220state`.

Открыть его сразу, если проверка уже выполнена в этой рабочей папке:

```powershell
powershell.exe -NoProfile -STA -File emulator/window.ps1 -Firmware analysis/firmware-patches/ui-label/b220-mod.bin -LoadState analysis/firmware-patches/ui-label/proof/working-title.b220state
```

Снимок открывается на паузе. Кнопка «Продолжить» возобновляет исполнение.

Выбрать образ вручную можно через «Прошивка…»:
`analysis/firmware-patches/ui-label/b220-mod.bin`.
Он использует собственные NOR/SD по SHA-256. Интернет HLE остаётся отключён
для изменённых образов. Проверка рисунка выполнена в эмуляторе; аппарат пока
не доступен для сверки.

## Восстановленный интерфейс

Адреса относятся только к исходному PS этой сборки B220.

| Адрес | Назначение |
|---|---|
| `0x005b7dd0` | Исходный Thumb BL графической функции; здесь стоит наш переход |
| `0x004cf432` | Штатный рендерер текста; имя в исходниках неизвестно |
| `0x001294d8` | Исходная строка «Время» в UTF-16 BE |
| `0x004220a4` | Наша условная обёртка, 36 байт с литералами и выравниванием |
| `0x00422880` | Новая строка `B220 MOD`, 18 байт с завершающим нулём |
| `0x005b7dd4` | Возврат из штатного рендерера в вызывающий код |

На наблюдаемом вызове графическая функция получает:

| Параметр | Значение/роль |
|---|---|
| R0 | Указатель на рабочую область прямоугольника |
| R1, R2 | Упакованные 16-битные координаты; в проверке `0x00050000`, `0x00aa0015` |
| R3 | Указатель на текст UTF-16 BE |
| `[SP]` | Число 16-битных символов: исходно 5, после вставки 8 |
| `[SP+12]` | Наблюдаемый аргумент шрифта, в проверке 6 |
| Остальные стековые аргументы | Исходные цвет/стиль и прочие параметры, передаются без изменений |

Первый исследовательский вариант был привязан к соседней ветке отрисовки;
он не дошёл до нужного заголовка. Рабочие адрес и параметры установлены
остановкой **перед реальным BL**, затем проверены на входе рендерера.

Обёртка сохраняет R4, сравнивает R3 с точным указателем исходной строки и
подменяет только совпадение. В этой ветке она записывает новую длину в исходный
исходящий аргумент `[SP]`. Перед `BX` восстанавливаются R4 и исходный SP;
стек не сдвигает дополнительные аргументы. LR после исходного BL уже содержит
правильный адрес возврата, поэтому используется хвостовой вызов рендерера.
IP/R12 служит временным регистром; штатный рендерер сам заменяет его в прологе.

Вызывающая функция после возврата переходит прямо к освобождению своего
кадра по `0x5b7d08`: изменённый исходящий аргумент длины ей больше не нужен.
Для остальных указателей строки R3 и `[SP]` сохраняются; проверена эта ветка
обёртки, а не только путь новой надписи.

Срабатывание привязано к указателю строки в этой ветке рисования, а не к
отдельно проверяемому ID окна. Любое другое её использование с тем же
указателем тоже получит новую надпись. Другой язык может выбрать другой
указатель и пройти без замены. Это первый графический вызов из нашего кода;
отдельное приложение или собственное окно ещё не создаётся.

## Размещение кода и строки

Сохранён первый перехват из `build_key_marker.py`. Дополнительно используются
два строго ограниченных JPEG-слота по 599 байт:

- В ресурсе `0x421e7c` удалены APP0/APP13/APP14 (48 байт). Проверены обычные
  YCbCr-компоненты и совпадение декодированных пикселей; в хвост после EOI
  помещена обёртка с литералами.
- В ресурсе `0x42263b` удалён только APP0/JFIF (18 байт). Эти байты после
  нового EOI занимает UTF-16-строка с терминатором.

Размер PS, адреса начала и размеры слотов сохранены. Сборщик проверяет точный
хеш оригинала, исходный BL, JPEG-ресурсы, границы и побайтовое совпадение RGB
до и после удаления метаданных. Отдельный показ этих двух изменённых картинок
штатным просмотрщиком пока не проверялся. Большие payload потребуют другого
размещения; случайные диапазоны `FF` и RAM свободными не объявляются.

## Воспроизведение

```powershell
.\.venv\Scripts\python.exe -m tools.build_ui_label
.\.venv\Scripts\python.exe -m unittest tests.test_ui_label_patch -v
.\.venv\Scripts\python.exe -m tools.prove_ui_label
```

Проверка по умолчанию начинает холодную загрузку выбранного образа.
`--load-state` допускает валидированный снимок **этого же PS** до пятого кадра
заставки. При разработке использовано продолжение раннего снимка
`early-boot.b220state`, полученного после 15,4 секунды холодного старта этого
же образа. Подмена ROM/RAM внутри снимка другого образа не используется.

Сборщик — [build_ui_label.py](tools/build_ui_label.py), описание Thumb-кода —
[ui_label.S](patches/ui_label.S), проверка — [prove_ui_label.py](tools/prove_ui_label.py).
Как и в первом патче, машинные кодировки пока заданы непосредственно;
`.S` документирует их, внешний ARM-ассемблер автоматически не запускается.

## Проверено

Результат 2 ноября 2026 года, SHA-256 образа:
`c79b72feb7e4a822c241526ebac28cc445d27857b5a5b3cd569c3ab5efe8c2a5`.

- Два теста: воспроизводимость/границы/пиксели и обе ветки обёртки с проверкой
  регистров и всех остальных стековых аргументов — PASS.
- Настоящая клавиша переводит окно даты в окно времени, без записи регистров
  или RAM проверочным инструментом.
- На входе штатного рендерера R3=`0x422880`, `[SP]=8`; SP, LR, координаты,
  остальные стековые аргументы и сохраняемые регистры корректны.
- Нативный код прочитал все восемь символов: зафиксированы 42 чтения новой
  строки из ROM, затем штатный возврат и полный кадр LCD.
- На кадре виден **B220 MOD**, отрисованный гостевым шрифтом.
- В том же прогоне дважды сработала прежняя вставка, записывающая `B220` в RAM.
- После дополнительного исполнения проверены стрелка вверх (время `10:00`)
  и подтверждение: прошивка возвращается на главный экран.
- Исходные ZIP, PAC, PS, NV и извлечённые ресурсы проверены без изменений.

Остановка ровно на счётчике полного LCD-кадра может предшествовать завершению
нативной операции рисования. При дальнейшем вводе в части контрольных
прогонов заголовок исчезает; это воспроизведено и на оригинале в такой же
точке остановки. Дополнительное исполнение улучшает результат, но устойчивость
этой перерисовки ещё предстоит разобрать. Рабочий снимок получен после
дополнительного исполнения, а `visible.b220state` оставлен как снимок
непосредственно контрольного кадра. В обычном окне на этом кадре
автоматической паузы нет.
