# Полные снимки состояния эмулятора

Первый консольный этап: `--save-state` и `--load-state` в `emulator.run`.
Снимок сохраняет CPU, память и моделируемые устройства, поэтому продолжение
начинается с сохранённого PC. Исходные файлы прошивки используются только для
чтения и проверки совместимости.

Для отдельного PS используйте `--firmware <копия.bin>` и при сохранении, и
при восстановлении: SHA-256 выбранного образа должен совпадать со снимком.
Точки останова и окна отладчика в снимок не входят.
[Выбор образа и отладчик](DEBUGGER_RU.md).

## Сохранить состояние после загрузки

```powershell
.\.venv\Scripts\python.exe -m emulator.run --explore --instructions 200000000 --seconds 180 --frames 5 --save-state analysis/emulator/snapshots/screen.b220state --out analysis/emulator/snapshots/screen.json
```

Для состояния перед конкретной функцией вместо `--frames 5` можно использовать
`--until 0x17e8fc`. Сохранение происходит после остановки CPU: по адресу,
числу кадров, инструкционному или временному лимиту.

## Загрузить и продолжить

```powershell
.\.venv\Scripts\python.exe -m emulator.run --load-state analysis/emulator/snapshots/screen.b220state --instructions 1000000 --seconds 30 --save-state analysis/emulator/snapshots/continued.b220state --out analysis/emulator/snapshots/continued.json
```

В результате появляются JSON/HTML-отчёт и PNG текущего экрана.
`--live-frame analysis/emulator/snapshots/live.png` дополнительно обновляет PNG
во время выполнения. При загрузке сразу публикуется и сохранённый кадр.

Для загрузки нужно указать тот же профиль, с которым создан снимок. Обычный
профиль выбирается автоматически; свой задаётся через `--profile путь.json`.
Режим `--explore` берётся из снимка. `--load-flash` и `--load-state` взаимоисключающие.

`--frames N` при загрузке означает N дополнительных полных перерисовок.
Инструкционный и временной лимиты относятся к новому прогону. Исходные лимиты
и причина предыдущей остановки не возобновляются автоматически.

Обычный файл `window-nor-v2.bin` этими командами не перезаписывается.
Виртуальная NOR находится внутри снимка. Отдельный файл NOR записывается
только при явном использовании существующего `--save-flash`.

## Подготовленные локальные примеры

В рабочей папке проверены:

* `analysis/emulator/snapshots/home.b220state` — домашний экран.
* `analysis/emulator/snapshots/wallpaper.b220state` — предпросмотр обоев.

Оба можно подставить в команду `--load-state`. Это локальные артефакты;
Git исключает файлы `*.b220state`. Их совместимость зависит от версии модели,
поэтому при изменениях эмулятора может потребоваться создать их заново.

## Состав снимка и ограничения версии 1

Файл `.b220state` — ZIP с `manifest.json` и двоичными блоками памяти.
Одинаковые блоки хранятся один раз, каждый проверяется по размеру и SHA-256.
Запись атомарная: ошибка замены сохраняет предыдущий файл.
Содержимое не использует pickle, объекты Python или нативный контекст Unicorn.

Сохраняются:

* Общие и банковые регистры ARM, CPSR/SPSR, ARM/Thumb и доступные модели
  регистры CP15. Регистры читаются через API Unicorn; банковые регистры — из
  временного контекста. Набор CP15 сопоставлен с
  [ARM926EJ-S Technical Reference Manual, глава 2](https://documentation-service.arm.com/static/5e8e3d1088295d1e18d3a9b2).
* RAM, SRAM, общая память, отображённые MMIO-страницы и виртуальная NOR.
  Алиас `0x34000000` после загрузки использует ту же RAM, что и `0x04000000`.
* Состояния LCD, JPEG, DMA, IRQ, таймеров, RTC, SPI, обмена с DSP и клавиатуры,
  включая очереди и незавершённые операции моделируемых устройств.
* Виртуальный счётчик блоков, сроки событий и текущий кадр.

Формат проверяет хеш исходной прошивки, профиля, исходников аппаратной модели
и версии Unicorn/Pillow. Версия 1 принимает только совместимую текущую модель;
автоматической миграции старых снимков пока нет. Исследовательские `.pkl.gz`
остаются отдельным внутренним форматом и не принимаются через `--load-state`.

Часы компьютера, файловые каналы команд, callbacks, пути вывода и управление
окном не сохраняются. Общий журнал Board и счётчики профилирования начинают
новый участок наблюдения. Внутренние данные и счётчики устройств сохраняются.

После сохранения и загрузки очищается кэш трансляции: это обеспечивает одинаковое
продолжение в текущей модели времени, основанной на числе блоков. Развитие самой
модели времени остаётся отдельным этапом плана.

Штатная загрузка сейчас доступна через консоль. Кнопки сохранения и загрузки
в WinForms — следующий небольшой этап; сочетание `--interactive --load-state`
пока даёт явное сообщение об этом ограничении.

## Проверка

Добавлены восемь проверок: продолжение в новом процессе, восстановление ARM/Thumb
и банков IRQ, таймеров и очереди ввода, RAM-алиаса, частичных операций устройств,
отказ при несовместимости и повреждении, сохранение предыдущего файла при ошибке.
Сравнение на исходной прошивке включает продолжение прямо с вектора настоящего IRQ.
Полный набор: **52 теста, PASS**.

На домашнем экране и в предпросмотре обоев проверена схема:
сохранить S → выполнить последовательность K → получить A;
загрузить S в новый движок → выполнить ту же K → получить A снова.
Совпадают регистры, память, NOR, LCD и состояния таймеров.
Локальный отчёт: `analysis/emulator/snapshots/continuation-check.json`.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_snapshot.py -v
```
