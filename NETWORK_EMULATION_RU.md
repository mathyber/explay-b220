## Вывод

Практичная цель — дать штатному браузеру доступ к сети через Windows,
предоставив прошивке виртуальное пакетное соединение. Реальную SIM-карту
и подключение к мобильному оператору для такого стенда можно заменить
виртуальными службами внутри эмулятора.

Предпочтительная архитектура для исследования самой прошивки: сохранить
исполнение её TCP/IP и подключить передачу/приём пакетов к сетевому backend
на компьютере. Сокетная HLE — альтернативный способ быстрее проверить браузер,
если граница пакетного интерфейса окажется слишком сложной.

Это вывод о подходе. Возможность подключения через конкретный найденный API
ещё предстоит подтвердить трассировкой реального запроса браузера.

Не установлены: точная реализация TCP/IP, вход/выход IP-пакетов, внутренний ABI
сетевых сообщений и полный набор проверок SIM/регистрации. Название lwIP
по исследованным данным не подтверждено.

Строки `PPP_AUTHNAME`, `PPP_AUTHSECRET` и подобные также найдены, но они могут
относиться к provisioning. Они не доказывают, что внутренний путь браузера
к передаче данных построен на PPP. Если PPP действительно потребуется,
он включает согласование канала и сетевых параметров, а не просто передачу
готовых IP-пакетов. [RFC 1661](https://www.rfc-editor.org/rfc/rfc1661.html),
[IPCP — RFC 1332](https://www.rfc-editor.org/rfc/rfc1332.html).

Наличие ATC-обработчиков и вызова `MNGPRS_SendDataReq` также не устанавливает,
что браузер управляет отдельным UART-модемом командами AT. Найденный путь
браузера использует внутренние сетевые функции и сообщения APP_MN.

## Где сейчас обрыв

У эмулятора нет сетевого backend. `EmptySpi` воспроизводит тактирование
без ответа подключённой карты/переключателя, а `DspBootstrap` выполняет
начальный обмен загрузки DSP. Регистрация в сети, GPRS-сессия и передача
пользовательских пакетов ими не реализованы.

Для браузера нужно согласовать две части:

1. **Управление соединением:** готовность выбранной SIM, состояние регистрации,
   разрешение пакетных данных, APN/PDP, адрес и DNS, отключение и ошибки.
2. **Передачу данных:** отправка, приём, доступность буферов и уведомления задач.

Реальный GPRS имеет отдельные процедуры регистрации и установления PDP.
В стенде их можно представить виртуальными службами с теми событиями,
которые ожидает прошивка. Форматы этих событий надо восстановить.
[3GPP TS 24.008, раздел 6](https://atis.org/wp-content/uploads/3gpp-documents/Rel99-14/ATIS.3GPP.24.008V5160-2007.pdf).

Один нарисованный значок GPRS или успешный ответ создания сокета не обеспечит
получение страницы. Нужна согласованная последовательность состояний и данных.

## Три уровня реализации

| Подход | Что выполняет прошивка | Что добавляем в эмулятор | Оценка |
|---|---|---|---|
| Полная модель мобильной связи | SIM/телефонный стек и нижние уровни связи в пределах точности модели | Контроллеры SIM, взаимодействие с DSP/baseband, виртуальная сеть и согласованные радиособытия | Самый большой исследовательский проект |
| Пакетное подключение | Браузер, сокеты, DNS и TCP/IP | Виртуальные службы готовности/соединения, границу пакетов, backend Windows | Предпочтительная цель для исследования штатного сетевого стека |
| Сокетная HLE | Браузер и его верхние протоколы в зависимости от выбранной точки перехвата | Сетевые API и их асинхронные события через сокеты Windows | Возможный более короткий прототип, но ABI ещё не восстановлен |

HLE означает, что соответствующий вызов обслуживает эмулятор: читает аргументы,
получает результат от Windows и возвращает данные/события в гостевую систему.
Исходный файл прошивки остаётся прежним. При этом исполнение части её сетевого
кода заменяется моделью; такой режим надо явно учитывать при проверке прошивки.

Возможен гибрид: виртуальные службы SIM/регистрации/PDP и штатный TCP/IP.
Именно его предлагается исследовать первым. Начальный вариант — одна
виртуальная SIM; остальные слоты остаются без карты, чтобы ограничить объём.

## Подключение к Windows

Целевая схема:

```text
Браузер CMS → сокеты/DNS/TCP/IP прошивки
                         ↕
           виртуальный пакетный канал
                         ↕
            адаптер пакетов + backend
                         ↕
                 сеть Windows
```

Для пакетного варианта кандидат — пользовательский NAT/backend наподобие
libslirp. Такая архитектура используется QEMU для подключения гостя к сети
через хост. У нас потребуется собственное сопряжение с телефоном:
драйвера обычной виртуальной Ethernet-карты у этой прошивки пока не обнаружено.
[Сетевая архитектура QEMU](https://www.qemu.org/docs/master/system/devices/net.html).

API libslirp принимает/возвращает Ethernet-кадры, предусматривает виртуальные
часы, таймеры и polling сокетов; в заголовке есть поддержка Windows.
Если у телефона на найденной границе будут сырые IP-пакеты, понадобится
адаптер Ethernet/ARP ↔ IP. Сборка и интеграция libslirp в наш процесс ещё
не проверялись. [Заголовок API libslirp](https://qemu.googlesource.com/libslirp/+/refs/heads/master/src/libslirp.h).

Для сокетной HLE достаточно хостовых TCP/UDP-сокетов, но потребуется правильно
воспроизвести guest handles, структуры big-endian, ошибки, частичные send/recv,
закрытие, DNS, таймауты и уведомления задач. Сетевое ожидание не должно
блокировать исполнение телефона и интерфейс Windows.

## Интернет и совместимость сайтов — разные проверки

Первый результат — простая страница на контролируемом HTTP-сервере компьютера.
Проверяем реальный запрос из браузера, ответ и отображение уникального текста,
затем картинку, переход по ссылке и повторное соединение. После этого проверяем
выход на внешний HTTP-сервер.

HTTPS требует отдельного исследования библиотеки: строки crypto/RSA/X.509
не устанавливают поддержку TLS 1.2 или 1.3. TLS 1.0 и 1.1 официально устарели,
поэтому совместимость со многими серверами может стать ограничением.
[RFC 8996](https://www.rfc-editor.org/rfc/rfc8996.html).

Также надо измерить возможности самого CMS: HTML/WML/XHTML, JavaScript/CSS,
кодировки, cookies, редиректы, размеры страниц и память. Появление IP-связности
не добавит браузеру отсутствующих возможностей отображения.

По явному решению пользователя адаптация современных сайтов исключена из
задачи. TLS исполняет прошивка, HTTP-заголовки и содержимое страниц передаются
без изменений. Прокси с завершением TLS, обновление версии TLS за телефон,
обход сертификатов и упрощение HTML не используются.

По выбранному профилю может также понадобиться WAP-шлюз. В стандартах есть
как HTTP-путь, так и WSP/WTP; наличие надписи WAP ещё не определяет используемый
протокол. [OMA Wireless Application Environment](https://openmobilealliance.org/release/Browsing/V2_1-20031113-C/OMA-WAP-WAESpec-V2_1-20020909-C.PDF).

## Время, пауза и снимки состояния

Сеть Windows живёт в реальном времени, телефон сейчас использует счётчик
блоков. Нужно определить, когда входящие события становятся видимы гостю,
что происходит при паузе и как ограничиваются буферы. Это аргумент в пользу
доработки времени перед устойчивой живой сетью.

Открытый сокет Windows нельзя просто включить в `.b220state` и позже продолжить
существующее соединение с внешним сервером: удалённая сторона продолжает жить
вне снимка. Для первых режимов разумно сохраняться без активных соединений,
а для воспроизводимых сетевых тестов записывать ответы/пакеты и воспроизводить
их по виртуальному времени. Политика снимков живой сети потребует отдельной
реализации; текущий формат этого не делает.

## Практический результат N1: первый отказ браузера

Добавлены `emulator/network_trace.py` и ключ консольного запуска
`--network-trace <файл.json>`. Наблюдатель фиксирует сетевые сообщения прошивки,
переходы окон, проверки SIM и входы в известные функции CMS/DNS/socket.
Он не меняет память/регистры гостя и не открывает соединений Windows.
Адреса привязаны к SHA-256 исходной PS; размер журнала ограничен 10000 событиями,
счётчики и число отброшенных событий записываются отдельно. Аргументы и
возможные строки — сырые наблюдения, а не восстановленные сигнатуры API.

На исходной прошивке проверен путь «Меню → Интернет → Дом. страница»:

* Меню браузера имеет ID `0x40001`; ввод URL открывается без SIM.
* При выборе домашней страницы код `0x58d704` вызывает проверку `0x4b03c4`
  для текущего слота 0. Чтение статуса `0x4adf4c` возвращает `7`, проверка — `0`.
  Фоновые проверки слотов 1 и 2 также показывают статус `7` и отказ.
* В точке `0x58d708` результат равен нулю; переход ведёт через `0x58d848`
  к уведомлению `0x4b0574`. Открывается окно `0x26` с текстом «Нет SIM».
* Ни один из наблюдаемых входов CMS socket/DNS/connect/send не достигнут.
  Для этого сценария отказ происходит до сетевого соединения. Запрос PDP и
  формат его подтверждения ещё предстоит проверить после виртуализации SIM.

Кадр сохранён в `analysis/emulator/network/sim-confirmed/01-ok.png`, журнал —
рядом в `network-trace.json`. Это результаты локального прогона, они не входят
в Git. Долгий прогон успевает закрыть уведомление по таймеру, поэтому для его
фиксации использован бюджет 1 млн инструкций.

Для повторения нажатий появился отдельный инструмент. Например, из уже
подготовленного снимка с открытым меню браузера:

```powershell
.\.venv\Scripts\python.exe -m tools.network_probe --load-state analysis/emulator/network/05-browser.b220state --steps down --out analysis/emulator/network/repeat-menu
.\.venv\Scripts\python.exe -m tools.network_probe --load-state analysis/emulator/network/repeat-menu/01-down.b220state --steps ok --instructions 1000000 --out analysis/emulator/network/repeat-sim
```

`--out` должен быть новым или пустым каталогом. После каждого шага сохраняются
PNG, полное состояние и общий JSON-журнал; `wait` означает продолжение без
нажатия. Отключённая подсветка может поглотить первую клавишу для пробуждения:
инструмент специально не добавляет скрытых нажатий. Исходный снимок и
виртуальная NOR обычного оконного запуска не перезаписываются.

Для наблюдения обычного консольного прогона:

```powershell
.\.venv\Scripts\python.exe -m emulator.run --load-state analysis/emulator/network/05-browser.b220state --instructions 1000000 --network-trace analysis/emulator/network/observe.json --out analysis/emulator/network/observe-run.json
```

После первого отказа добавлен отдельный экспериментальный режим подготовки
SIM/пакетной регистрации в эмуляторе и виртуального подтверждения PDP.
Одного успешного возврата из проверки SIM недостаточно: нужны согласованные
состояния служб, события и настройки APN. Исходный образ прошивки не меняем.

Проверки этого изменения: 55 тестов проходят, включая сравнение регистров и
гостевых часов с наблюдателем/без него, ограничение журнала и снимок при
подключённом наблюдателе. CLI с `--network-trace` проверен отдельным прогоном.
`tools.verify_artifacts` подтверждает неизменность 8 исходных файлов, 4
компонентов PAC и 31 извлечённого ресурса.

## Лабораторное подключение: SIM1 → PDP → DNS

Первое состояние сохранено коммитом `f4ba946`. Следующий шаг реализован в
`emulator/virtual_network.py`, включается **только** флагом `--virtual-network`
инструмента `tools.network_probe`. Обычный оконный запуск этот режим не включает.

Это прототип службы подключения на уровне вызовов прошивки (HLE). Он задаёт
известные кэши в RAM для SIM1 и предпосылки пакетной регистрации. В первом
прототипе он также переключал первый профиль на WAP2/HTTP: пустой WAP1-шлюз
мешал проверить путь данных. Сейчас это переключение оставлено только для
явного локального `--http-test`. По умолчанию WAP-настройки сохраняются;
`--sim-plmn` запускает оригинальную инициализацию операторских профилей по
домашнему MCC/MNC виртуальной SIM. Это не произвольная подстройка сайта.

Один кэш SIM не решает задачу. При штатной активации обработчик `0x240252`
читает структуру пакетной службы `0x0434c4b4` с шагом `0x34` на слот:
проверяет слово `+0`, статус `uint16 +0x0c` и байт `+0x14`. Исходные значения
`0 / 0xffff / 0` приводят к отказу `0x66` через `0x24028a`. Это подтверждено
реальными двумя сообщениями `APP_MN_CMS_ACTIVATE_PDP_CONTEXT_CNF`, а не только
просмотром инструкций. В лаборатории используются значения `1 / 1 / 1`;
точные названия перечислений ещё не восстановлены, это явные экспериментальные
предпосылки, а не полная модель регистрации оператора.

Виртуальная служба перехватывает этот обработчик только для слота 0 и клиента
`0x15`. Проверяет сообщение `0x13f4`, длину `0x40`, режим выбора и список с
контекстом 1. Затем вызывает исходный помощник ответа `0x53b044` с результатом
0. Инструкции PS не переписываются: перенаправляется выполнение CPU, а память
запроса остаётся под управлением штатного диспетчера. Подтверждение выделяет
и доставляет сама прошивка через свою очередь. Неизвестный формат запроса
останавливает эксперимент, успешный ответ для него не выдумывается.

Проверенная цепочка на URL `http://a.aa`:

1. Проходит штатная проверка SIM1, остальные два слота остаются без SIM.
2. Прошивка запрашивает активацию PDP и получает тело подтверждения
   `uint32 result=0, uint32 slot=0` в big endian.
3. Сама обрабатывает `NETLINK_SUCCESS` / `MSG_CMSBRW_OPENNETSUCCESS`.
4. Вызывает `cms.socket`, получает гостевой сокет, затем `cms.dns` и
   нижнюю DNS-функцию `0x2cf9c6` с именем `a.aa`.
5. Лабораторный режим останавливает CPU перед выполнением DNS с причиной
   `virtual network boundary / DNS backend not implemented`.

В этом офлайн-прогоне адрес использовался только как тестовый ввод. Запросов к
DNS Windows, оператору и внешним серверам не было. Отдельный режим `--internet`
теперь подключает DNS и TCP Windows; сам `--virtual-network` по-прежнему
останавливается перед DNS и не заменяет эмуляцию SIM-контроллера/DSP.

Повторить на подготовленном локальном снимке ввода URL:

```powershell
.\.venv\Scripts\python.exe -m tools.network_probe --load-state analysis/emulator/network/url-input/04-2.b220state --steps soft_left --instructions 9000000 --virtual-network --out analysis/emulator/network/my-virtual-http
```

Для получения этого снимка из сохранённого редактора, где уже есть `http://`:

```powershell
.\.venv\Scripts\python.exe -m tools.network_probe --load-state analysis/emulator/network/06-url.b220state --steps 2,1,2,2 --instructions 4000000 --out analysis/emulator/network/my-url-input
```

Клавиши через штатный ввод набирают `a.aa`. Во второй команде снимок с готовым
адресом будет `my-url-input/04-2.b220state`; его можно передать в первую.
При включении проверяются хеш PS, открытое окно браузера/редактора, профиль 0
и ожидаемая структура RAM. Неподходящий снимок отклоняется до изменения RAM.

В выходном каталоге находятся PNG, `network-trace.json` и
`virtual-network.json`: последний содержит точный список изменений RAM,
стадию подключения и события виртуальной службы. В режиме эксперимента
`.b220state` не создаются. Штатное сохранение такого Board также отклоняется:
формат снимка пока не умеет сохранять HLE-сервис. Работающее обычное окно,
его файл NOR и входной снимок не затрагиваются.

Сопутствующее исправление: на этом пути прошивка выводит область 32 × 19
через **DMA 17** (`config=0x04880040`, `count=1216`, `frame=0x122`, шаг исходных
строк 352 байта). Раньше этот канал допускал только RAM-копии; теперь оба
программных канала 16/17 поддерживают уже известный формат LCD. Завершение и
очистка битов остаются раздельными. Сохранённые старой моделью состояния
несовместимы по хешу исходников; подготовленные локальные снимки home,
wallpaper и необходимые снимки браузера перенесены на текущую модель.

Этот режим по-прежнему заканчивается на явной границе DNS. Отдельный
`--http-test` использует локальный сервер; `--internet` — реальный DNS и TCP.
Дальнейшая работа — окно, аппаратная SIM, полный жизненный цикл PDP и сохранение.
