# Explay B220: разбор прошивки и путь к собственному коду

> Продолжение исследования: [эмуляция уже доходит до заставки EXPLAY](EMULATION_RU.md).
> Ниже сохранён первоначальный разбор; актуальные модели периферии и точка остановки описаны в продолжении.

Дата исследования: 31 октября 2026 года. Исследован именно переданный пакет `Explay_B220_M224_V02.02_B06_20120720_FSPD`, без подключения телефона. Отсутствие штатной установки сторонних приложений принимается как установленный владельцем факт.

**Основной вывод:** это доступная для дальнейшего реверса монолитная прошивка Spreadtrum семейства **SC6600L**, сборка под **L7A**, с кодом **ARM/Thumb big-endian**. Важные участки читаются без распаковки и расшифровки. Запуск своего нативного кода представляется технически реалистичной целью. Поддержка J2ME потребует отдельного порта среды исполнения и библиотек. Готового проверенного эмулятора именно B220/SC6600L, который загружает этот образ и показывает рабочее меню, в изученных источниках не найдено.

В папке уже есть извлечённые компоненты, каталог медиа, карта старта и работающий под Windows эксперимент исполнения начальных инструкций. **Рабочее меню телефона в эмуляторе пока не получено.**

## Что подтверждено и что ещё является гипотезой

| Положение | Уверенность и основание |
|---|---|
| Платформа прошивки — SC6600L | Подтверждено названием PAC-продукта, XML, именем PS и диагностическими строками |
| Сборка рассчитана на L7A | Прямо указано в имени PS; маркировка физического кристалла не прочитана |
| ARM/Thumb, big-endian код и данные | Подтверждено векторами, осмысленным дизассемблированием, литералами, таблицами и исполнением |
| Ядро семейства ARM7TDMI, ARMv4T | Соответствует платформе SC6600 и наблюдаемому коду; конкретный CPU ID устройства не считан |
| NOR около 8 MiB, RAM около 4 MiB | Сильная рабочая гипотеза по `64X32`, размеру PS и адресам RAM; физический тип и ёмкость микросхем не измерены |
| Экран 176×220 | Подтверждается размерами заставки и тестового изображения; выбранный на конкретной плате LCD-контроллер ещё неизвестен |
| ОС — встроенная RTOS со штатным MMI и телефонным стеком | Подтверждается кодом, очередями, потоками и диагностикой; конкретное происхождение ядра не установлено |
| Работающая штатная JVM отсутствует | Согласуется с наблюдением владельца; сигнатуры типичной Java-среды в PS не найдены |
| Можно выполнить неподписанный пользовательский FDL | Правдоподобный путь для этой платформы; на этом экземпляре телефона ещё не проверен |
| RAM в режимах штатной прошивки и FDL является одной памятью по разным адресам | Рабочая гипотеза стенда, а не восстановленная полностью схема remap |

SC6600 нельзя автоматически считать SC6530/SC6531. Первичная документация Spreadtrum указывает ARM7TDMI для серии SC6600, тогда как современные проекты для соседних семейств имеют другие требования к CPU и периферии. См. [годовой отчёт самой Spreadtrum, таблицы продуктов](https://www.sec.gov/Archives/edgar/data/1287950/000114420411020453/v217689_20f.htm).

## 1. Что лежало в архиве

ZIP имеет размер 4 316 345 байт. Его проверка CRC прошла. Все 8 обычных файлов в распакованном каталоге побайтно совпадают с ZIP.

В каталогах `Driver`, `SPD Upgrade Tool` и `WriteIMEI Tool` находятся **интернет-ярлыки**, а не исполняемые программы или драйверы. Файл `Credits.txt` указывает на сторонний сайт распространения. Поэтому происхождение архива нельзя независимо удостоверить как официальный дистрибутив производителя, хотя внутренние идентификаторы согласованы.

Сам PAC:

| Поле | Значение |
|---|---|
| Имя | `S915D_B220_QCIF_N_TRI_M224V02.02B06.pac` |
| Размер | 7 697 027 байт |
| Версия контейнера | `BP_R1.0.0` |
| Продукт | `NOR_FLASH_6600L` |
| Сборка | `S915D_B220_QCIF_N_TRI_M224V02.02B06` |
| Каталог | `0x84C`, шесть записей по `0xA14` байт |
| SHA-256 | `00d8ac78fd637571a39c4a653f964d2cbd18e2274b7eb80ceaa07dd45c18b65a` |

У этой старой разновидности контейнера поле magic и оба поля CRC равны нулю. Это **не успешная проверка PAC CRC**. Наш распаковщик отдельно сообщает, что эти проверки отсутствуют в данном архиве. Целостность исходника подтверждается ZIP CRC, совпадением распакованных файлов и зафиксированными SHA-256.

Таблица файлов:

| ID | Содержимое | Смещение в PAC | Размер |
|---|---|---:|---:|
| FDL | `nor_fdl.bin` | `0x44C4` | 37 348 |
| NV | `nvitem_release.bin` | `0xD6A8` | 15 644 |
| PS | `SC6600L_S915D_B220_L7A_64X32_M224_qcif.bin` | `0x113C4` | 7 623 420 |
| FLASH | Операция, отдельного файла нет | — | 0 |
| PhaseCheck | Операция, отдельного файла нет | — | 0 |

Подробности и хеши: [pac_manifest.json](analysis/pac_manifest.json). Извлечённые файлы: [analysis/extracted](analysis/extracted).

Для проверки структуры использован открытый [исходник unpac](https://github.com/ilyakurdyukov/spreadtrum_flash/blob/main/unpac/unpac.c). Python-реализация добавляет обработку наблюдаемого старого заголовка, контроль границ и пересечений файлов. Формат полей контейнера little-endian; это не противоречит big-endian коду внутри.

## 2. Значение компонентов и адресов в XML

`nor_fdl.bin` — программа загрузчика для сервисного режима. Она исполняется на телефоне и обслуживает обмен с прошивальщиком. Это не штатная ОС и не загрузочный ROM чипа.

`PS` в этом пакете — основной большой образ. Название Protocol Station не означает, что там находится только радиопротокол: видны интерфейс, файловые операции, браузер, мультимедиа, драйверы и ядро.

`nvitem_release.bin` — шаблон NV из релизного пакета. Его нельзя считать резервной копией конкретного телефона: индивидуальные калибровки и служебные значения хранятся на устройстве.

XML задаёт:

| ID | Base | Смысл |
|---|---:|---|
| FDL | `0x34000000` | Адрес загрузки сервисной программы в память |
| PS | `0x80000003` | Логический идентификатор области для протокола прошивания |
| NV | `0x90000001` | Логический объект NV |
| FLASH | `0x90000003`, размер `0xC0000` | Операция стирания running-NV, в XML выключена |
| PhaseCheck | `0x90000002` | Производственная служебная область, в XML выключена |

**`0x80000003` не является адресом входа CPU.** Его нельзя передавать эмулятору как базу программы. Аналогично специальные идентификаторы NV нельзя трактовать как обычные физические адреса.

XML явно предусматривает сохранение Calibration, IMEI/IMEI2/IMEI3 и других NV-полей при обновлении. Это дополнительное основание сначала получать полный дамп устройства, а не считать PAC полным восстановительным снимком.

## 3. CPU, порядок байтов и начало исполнения

Первые 32 байта PS содержат восемь одинаковых ARM-команд:

```text
00000000: E59FF018   LDR PC, [PC, #0x18]
00000004: E59FF018   LDR PC, [PC, #0x18]
...
```

При ARM little-endian эти байты дают бессмысленные для старта команды. При ARM big-endian получается нормальная таблица исключений. С учётом ARM PC+8 первый переход читает слово по `0x20` и попадает на `0x006A4228`.

Векторы PS:

| Вектор | Адрес обработчика |
|---|---:|
| Reset | `0x006A4228` |
| Undefined | `0x006A4494` |
| SWI | `0x006A4500` |
| Prefetch abort | `0x006A4544` |
| Data abort | `0x006A45B0` |
| Reserved | `0x006A461C` |
| IRQ | `0x006A43E0` |
| FIQ | `0x006A4664` |

Таким образом, пригодная для анализа база PS — **`0x00000000`**, а не адрес из типового руководства по SC6531. В FDL база **`0x34000000`** подтверждается и XML, и собственными литералами загрузчика.

Код смешанный: ранний старт ARM, многие функции Thumb. Таблицы литералов, строки и изображения перемешаны с командами. Линейное дизассемблирование всего файла породит множество ложных инструкций. Нужны переходы по реальному управлению, отметки данных и отслеживание ARM/Thumb.

Это big-endian инструкции и данные старого ARM, а не современный BE8 с little-endian инструкциями. Не нужно предварительно переставлять байты всего файла: так будут испорчены строки и медиа.

Важные строки PS:

```text
0x00000498  S915D_B220_QCIF_N_TRI_M224V02.02B06
0x003B5A18  Project Version:   SC6600L_sp6601l_trisim
0x003B5A42  MMI Version:       SC6600L_sp6601l_trisim
0x003B5A92  HW Version:        SC6600L_sp6601l
0x003B5AB6  7-20-2012 9:59:54
0x00498BC2  Jul 20 2012
```

`sp6601l` здесь — строка проекта, её недостаточно для переименования физического чипа в SC6601. Аналогично `QCIF` в имени не заменяет измерение разрешения экрана.

## 4. Что стало известно о памяти и загрузке

Восстановлена таблица копирования/обнуления, на которую ссылается стартовый код по `0x00179D68`. Заголовок таблицы находится по `0x00179E34`.

| Действие | Источник в PS | Назначение в адресном пространстве CPU | Размер |
|---|---:|---:|---:|
| Копирование RW | `0x007237CC` | `0x04293600` | `0x2001C` |
| Обнуление ZI/BSS | — | `0x042B361C` | `0xEFCD8` |
| Копирование внутренней области | `0x0074432C` | `0x40003400` | `0x364` |
| Обнуление внутренней области | — | `0x40003764` | `0x78` |

Внешняя обнуляемая область заканчивается на `0x043A32F4`, не включая этот адрес. Следовательно, программа действительно рассчитывает на значительную RAM в диапазоне `0x04000000...`, а не только на несколько килобайт SRAM.

Рабочая карта:

| Диапазон/адрес | Наблюдение |
|---|---|
| `0x00000000...0x007452FB` | Загруженный PS с кодом, константами, ресурсами и образами RW |
| `0x04000000...` | Внешняя RAM в штатном режиме; подтверждена таблицей и указателями |
| `0x34000000...` | Память загрузки и работы FDL; связь с низкой RAM требует проверки remap |
| `0x40000000...` | Внутренняя исполняемая/рабочая память; FDL копирует туда код |
| `0x8000000C` | Самая ранняя запись PS в неизвестную периферию |
| `0x8B000018` | Самое раннее чтение FDL из неизвестной периферии |
| `0x20000014` | Регистр, читаемый при ранней настройке памяти/частот |
| `0x8400000C`, `0x84000004` | Статус/данные интерфейса, через который FDL ждёт синхронизацию |
| `0xFFFFFFFC` | Позднее раннее чтение PS; по дальнейшим сравнениям похоже на идентификатор аппаратуры |

Имена регистров не выдаются за установленные по datasheet: наблюдены адреса и операции, точное назначение части блоков ещё предстоит восстановить.

`64X32` обычно означает 64 Mbit flash и 32 Mbit RAM: 8 MiB и 4 MiB. Здесь это согласуется с бинарным содержимым. Однако границы пользовательской файловой системы, NV и служебных областей полностью не восстановлены. **Разницу между 8 MiB и длиной PS нельзя объявлять свободным местом для своего кода.** XML с размером операции NV тоже нельзя механически вычитать из длины образа.

Таблицы и точные границы: [startup_map.json](analysis/startup_map.json). Осмысленные фрагменты команд: [entrypoints.txt](analysis/entrypoints.txt).

## 5. ОС и прикладная среда

В PS присутствуют RTOS Compile Date, System Timer Thread, RTOS_Manage, RTOS_Manage_Queue, диагностические сообщения потоков и семафоров, компоненты `MMI...`, драйверы LCD, файловая и мультимедийная логика. Архитектура соответствует встраиваемому телефонному стеку с RTOS, MMI и аппаратно зависимой частью. Название MOCOR удобно как направление поиска родственной платформы, но точная версия SDK по этому исследованию не установлена.

Нельзя уверенно назвать ядро ThreadX только по производителю. Строки `ThreadX` не найдено; `Nucleus` как название ОС не найдено, а `nucleus` встречается в английском словаре ввода. Название конкретного RTOS потребует сравнения структур и кода планировщика.

Не обнаружены сигнатуры ELF, ZIP-приложений, стандартного Android-образа или `TRAPGAMI`/`DRPS`/`RRPS`/`COLB`/`CAPN`. В частности, известные stone-распаковщики не имеют здесь обнаруженного заголовка для начала работы. Это не доказательство отсутствия любой компрессии: часть картинок, шрифтов и таблиц может использовать собственные форматы.

Значимая часть машинного кода уже доступна непосредственно. Для первого нативного патча не требуется сначала полностью распаковать все ресурсы.

## 7. Почему строки Java не меняют исходный факт

Обнаружены:

```text
0x000DB672  ресурсная строка с JAVA Application (UTF-16BE)
0x003146CC  application/java-archive
0x00317224  text/vnd.sun.j2me.app-descriptor
0x0059D94C  mmiwap.c:CmsBrwJavaJadFile() in
0x0059DA58  mmiwap.c:CmsBrwJavaJarFile enter
0x006E4278  JAVA/LocalInstall (UTF-16BE)
```

Смещения ASCII-строк из сырого сканера могут включать один предшествующий печатный байт; выше для обработчиков приведено начало содержательной строки.

Два небольших Thumb-обработчика идентифицированы по обращениям к диагностике:

- `0x0059D888` — обработчик JAD; дальше вызывает общую браузерную логику.
- `0x0059D96C` — обработчик JAR; после диагностики вызывает обычные функции через межрежимные переходники.

Это полезные точки изучения загрузки файлов и возможной будущей интеграции. Их наличие не означает, что реализация установки MIDlet или JVM включена в сборку. Общие браузерные MIME-типы и строки интерфейса могли остаться от более широкой платформы.

В проверке сырых маркеров отсутствуют `java/lang`, `java.lang`, `javax/microedition`, `javax.microedition`, `CLDC`, `MIDP`, `MIDlet`, `JBlend`, `Jbed`, `KVM`, сигнатура Java class `CAFEBABE`. Единственное короткое совпадение `JVM` находится среди данных и само по себе ничего не доказывает. Не найдены и типичные `.mrp`, `.vxp`, `mythroad`.

Отрицательный поиск строк не является математическим доказательством отсутствия зашифрованной или полностью ROMизированной VM. Но **оснований рассчитывать на включение скрытой Java одним флагом нет**. Практический план должен исходить из создания новой среды исполнения. Проверка записана в [runtime_markers.json](analysis/runtime_markers.json), обработчики — в [java_jad_handler.txt](analysis/java_jad_handler.txt) и [java_jar_handler.txt](analysis/java_jar_handler.txt).

## 8. Что реально исполнено на Windows

Создан [boot_probe.py](tools/boot_probe.py) на Unicorn и Capstone. Он загружает неизменённый PS либо FDL, исполняет инструкции и пишет JSON с регистрами, хвостом трассы и причиной остановки. Он не обращается к USB и не пишет на телефон.

Два режима:

1. Строгий: неизвестная или защищённая память останавливает исполнение.
2. `--stub-zero-mmio`: для ограниченных диапазонов неизвестной периферии создаются нулевые страницы. Записи сохраняют значение, но аппаратной семантики у этих страниц нет.

Результаты текущего воспроизводимого прогона:

| Образ и режим | Сколько выполнено команд по счётчику hook | Результат |
|---|---:|---|
| PS, строгий | 6 | Запись `0x4FF7FFFF` в `0x8000000C` с PC `0x006A4238` |
| FDL, строгий | 22 | Чтение `0x8B000018` с PC `0x34000054` |
| PS, нулевые заглушки | 238 823 | Проходит копирование/обнуление и останавливается на чтении `0xFFFFFFFC`, PC `0x0048397C` |
| FDL, нулевые заглушки | 479 470 | Доходит до цикла ожидания регистра `0x8400000C`, PC `0x340008A6` |

В цикле FDL действительно есть проверка входного байта на `0x7E`, что согласуется с ожиданием синхронизации сервисного протокола. Это уже более содержательный результат, чем просто остановка на первой инструкции. Но выбираемый нулевыми регистрами UART/USB-путь может отличаться от устройства.

Ограничения стенда существенные:

- Unicorn не предоставляет модель ARM7TDMI; использован ARM926 как приближение.
- RAM 4 MiB и её отображения заданы как рабочая гипотеза; SRAM выделена 64 KiB, что не является измерением её ёмкости.
- Для совместимости с моделью движка удерживается его признак big-endian данных. Это не заявление о наличии CPSR.E у реального ARM7.
- Нулевые аппаратные заглушки могут выбирать неверные ветки и скрывать проблемы. Число выполненных команд не является процентом готовности эмулятора.
- Таймеры, прерывания, дисплей, DSP, SIM и файловое состояние устройства не воспроизведены.
- Штатный экран и меню не достигнуты. Результат не подтверждает работоспособность какого-либо прошивочного патча.

Отчёты: [PS strict](analysis/boot_probe_ps_strict.json), [FDL strict](analysis/boot_probe_fdl_strict.json), [PS с заглушками](analysis/boot_probe_ps_zero.json), [FDL с заглушками](analysis/boot_probe_fdl_zero.json).

[Unicorn](https://github.com/unicorn-engine/unicorn) — библиотека эмуляции CPU с поддержкой Windows, а не модель телефона. Проблемы режима и CPU требуют внимания даже в небольшом стенде; см. [официальный FAQ](https://github.com/unicorn-engine/unicorn/blob/master/docs/FAQ.md).

## 9. Можно ли получить полноценный эмулятор прошивки

Да, как отдельный проект реконструкции устройства. Из одного PAC автоматически получить точную модель аппаратуры нельзя. В нём отсутствуют встроенный Boot ROM чипа и снимок индивидуального состояния телефона, а описания периферии недостаточно.

Для цели «проверять собственные изменения до прошивки» полезны разные уровни:

| Уровень | Что выполняется | Сложность и польза |
|---|---|---|
| Отдельные функции | Декодеры, форматирование, части файловой логики | Наиболее быстрый путь к полезным проверкам |
| Свои приложения с общей HAL | Один исходник собирается для Windows и ARM | Быстро проверяет новую логику, графику и будущую VM; штатную ОС не исполняет |
| Штатное MMI с заглушенным радио | Настоящий образ, рабочий экран, клавиши, файловые операции | Разумная крупная промежуточная цель |
| Полная аппаратная эмуляция | ОС, радиочасть, DSP, SIM, Bluetooth, USB, все режимы | Гораздо больший объём работы, обычно лишний для первого пользовательского приложения |

Для запуска штатного MMI придётся добавить как минимум:

1. Корректные ARMv4T ARM/Thumb, big-endian, банковые регистры и исключения, переходы режимов и возвраты IRQ.
2. Проверенную карту NOR/RAM/SRAM, remap и достаточную модель контроллера памяти.
3. Аппаратный ID и несколько статусных регистров, от которых зависят ранние ветки старта.
4. Таймеры и контроллер прерываний, чтобы работали RTOS, задержки и клавиатурные события.
5. LCD-интерфейс, reset/read-ID, команды контроллера, RAM экрана и сохранение кадров.
6. Клавиатурную матрицу, GPIO и питание/ADC в объёме, необходимом для загрузки.
7. Модель flash/NV/файлового состояния; позднее — карту памяти.
8. По необходимости DMA и согласованные заглушки DSP/телефонного стека для режима без SIM/сети.

Следующая конкретная точка — чтение `0xFFFFFFFC`. Следует разобрать сравнительную таблицу, установить, какой ID ожидает сборка L7A, и сделать **явную конфигурацию аппаратного ID**, не выдавая произвольное число за считанное с телефона. Далее фиксировать новые регистры по трассе, а не обходить все проверки без анализа.

Нулевые заглушки нужны для разведки. Для полезного стенда проверки патчей каждую критическую заглушку следует заменить моделью: статус busy/ready, подтверждение IRQ, увеличение счётчика, очереди байтов, правила записи LCD. Нужны детерминированное время, снимки RAM/CPU и журнал аппаратных событий. Возврат в меню, файловые операции и отсутствие исключений должны проверяться явно.

QEMU можно использовать как основу отдельной модели платы. Команда с `-M versatilepb` либо произвольным `-kernel` не превращает его в SC6600L: карта периферии другой платы не совпадает. В опубликованном [списке ARM-плат QEMU](https://www.qemu.org/docs/master/system/target-arm.html) модели B220/SC6600L нет. Разработческий симулятор SDK под Win32 тоже не обязательно исполняет ARM-бинарник: такой симулятор может требовать перекомпиляции исходников SDK, которых в PAC нет.

Полный эмулятор не гарантирует точное поведение flash-питания, таймингов LCD и конкретной платы. Он способен значительно уменьшить число прошивок, но не полностью заменить завершающие испытания на устройстве.

## 10. Путь к собственному коду на телефоне

### Сначала RAM-программа через сервисный режим

FDL из пакета уже представляет собой нативную программу, загружаемую в RAM и запускаемую вне штатного интерфейса. Для собственного кода это перспективнее, чем искать уязвимость медиапарсера.

Открытый [UniFlash автора Luxferre](https://code.luxferre.top/luxferre/uniflash/src/branch/master/README.md) прямо содержит цель `sc6600l_generic` и поддержку одиночного FDL. Адрес `0x34000000` для нашей версии известен независимо из XML. В [коде протокола](https://github.com/aravindanve/uniflash/blob/master/unicmd.py) есть загрузка и запуск блока, чтение flash и специальные ответы. Это основание для инструментария, **не подтверждение успешного обмена именно с B220**.

Первый опыт на устройстве должен дать: определение сервисного интерфейса, версию Boot ROM/FDL, ID flash и два совпадающих полных дампа. Затем минимальная RAM-программа с наблюдаемым ответом — например, через уже разобранный транспорт, позднее тест экрана. Перенос готового FDL от другого семейства здесь не нужен: свой оригинальный загрузчик уже извлечён.

Пример синтаксиса для будущего readback, после подготовки UniFlash и проверки ёмкости:

```powershell
python uniflash.py -t sc6600l_generic `
  -sfdl D:\my-projects\EB220\analysis\extracted\nor_fdl.bin `
  -saddr 0x34000000 -l 0x800000 dump b220-full-1.bin
```

Это **не исполненная и не подтверждённая на телефоне команда**. `0x800000` — предполагаемые 8 MiB, длину следует сверить с физической flash. Имя target и параметры относятся к изученной версии UniFlash. Загрузчик исполняет инициализацию аппаратуры даже при readback; до первого обмена нельзя утверждать отсутствие любых побочных действий его кода. Bootkey, необходимость батареи и драйвер Windows ещё не определены. Универсально правильную клавишу по PAC вывести нельзя.

Исследовать транспорт сначала можно по оригинальному FDL, документируя HDLC-кадры и различие контрольных сумм Boot ROM/FDL. Простой пользовательский RAM-код затем может заменить FDL или быть запущен уже им, если конкретные команды и состояние памяти это допускают. **Поддержку исполнения неподписанного произвольного блока надо подтвердить отдельно.** Отсутствие `SPRD-SECUREFLAG` в образе этого не доказывает.

### Затем точечный патч штатной прошивки

Когда существует восстановление и проверенный RAM-код, следующий практичный результат — новая команда в штатном меню либо замена вызова одной встроенной функции на собственный обработчик.

Потребуется восстановить обработчики событий MMI, вывод на LCD, приём клавиш, таймеры, выделение RAM и доступ к файлам. Диагностические строки помогают находить функции. Их имена в таблице адресов должны сопровождаться хешем прошивки и степенью уверенности: одинаковое имя функции в другой версии не гарантирует прежний адрес.

Первый внедряемый модуль лучше делать простым плоским бинарником с фиксированной базой и маленькой таблицей импортов. Полноценный ELF-загрузчик потребует разбора секций, релокаций и соглашений ABI; штатной поддержки ELF пока не обнаружено.

Правила патча:

- Использовать копию образа и журнал ожидаемых исходных байтов, смещения, новых байтов и хешей.
- Не вставлять байты в середину PS: абсолютные адреса и таблицы немедленно сместятся. Начинать с замены фиксированного размера и переходника.
- Проверять ARM/Thumb, выравнивание и дальность переходов. Вызов Thumb-функции и переход в ARM не взаимозаменяемы.
- Восстанавливать вытесненные инструкции, регистры, стек и нужные флаги; сначала разобраться, выполняется ли обработчик в задаче или IRQ.
- Подтвердить свободную область ROM и RAM по карте реального устройства. Длинная последовательность `FF` сама по себе не является разрешением занять её.
- Проверить контрольные суммы и поведение инструмента записи на каждом слое отдельно: PAC, протокол FDL, возможная проверка PS.

Для ARM7 стартовые параметры собственного freestanding-кода ориентировочно: `-mcpu=arm7tdmi -marm -mbig-endian -mfloat-abi=soft -ffreestanding`. Для big-endian линковки требуется BE32; библиотеки тоже должны быть подходящего порядка байтов и ISA. Документация [GCC ARM options](https://gcc.gnu.org/onlinedocs/gcc/ARM-Options.html) описывает `-mbig-endian`, `-mbe32` и `-mthumb-interwork`. Совместимость со старым ABI прошивки, передача структур, выравнивание стека и функции компиляторной поддержки должны проверяться отдельно. Toolchain для ARM в этой сессии не установлен, payload не собран.

Для постоянного запуска удобен небольшой загрузчик приложения с microSD. Это тоже новый модуль: нужны SD/FAT, выбор файла, размещение и возврат в ОС. Наличие проекта sdboot для SC6531 не означает его пригодность для SC6600L. [FPDoom](https://github.com/ilyakurdyukov/fpdoom) заявляет SC6530/SC6531 и UMS9117; прямой поддержки исследуемой платформы он не устанавливает. Полезны идеи и протоколы, но аппаратный порт всё равно нужен.

## 11. Что понадобится для J2ME

Поддержка ARM и возможность запустить машинный код решают только нижний слой. `.jar` содержит Java-байткод и ресурсы; телефону нужны VM, библиотека классов и платформенный интерфейс.

Для типичных игр разумная цель — CLDC 1.1 и MIDP 2.0, с ограниченным набором расширений. Минимальная реализация должна включать:

| Компонент | Что нужно сделать |
|---|---|
| VM | Загрузка классов, интерпретация байткода, объекты, GC, исключения, потоки/мониторы, необходимые числовые операции |
| CLDC | `java.lang`, поддерживаемые части `java.io`/`java.util` и согласованная модель времени |
| MIDlet lifecycle | `startApp`, `pauseApp`, `destroyApp`, управление запуском |
| LCDUI | `Canvas`, `Graphics`, `Image`, `Font`, клавиши, события, repaint; позднее формы |
| MIDP game | `GameCanvas`, `Sprite`, `TiledLayer` для игр, которые их используют |
| Установка | ZIP/JAR, MANIFEST.MF, ресурсы, сохранение настроек; JAD по необходимости |
| RMS | Постоянные записи с предсказуемым поведением при выключении |
| Изображения/звук | PNG и базовые изображения; таймеры, тоны/мелодии и затем расширение MMAPI |
| Расширения | Nokia/Siemens/Samsung API по выбранным играм; JSR-75/82/184/прочие отдельно |

Первую графическую Java-программу можно получить с гораздо меньшим набором, чем широкую совместимость с библиотекой игр. Наличие работающего примера не означает совместимость MIDP 2.0 вообще.

Память: один экран 176×220 в RGB565 занимает **77 440 байт**, два — **154 880 байт**. К этому добавляются распакованные картинки, Java heap, стеки, классы, VM и RAM штатной ОС. Даже если физически есть 4 MiB, свободный Java heap не равен 4 MiB. Нужно измерить свободную память после старта и пиковое потребление выбранных приложений. Для ориентиров по влиянию изображений полезен [разбор памяти и производительности Java ME от Oracle](https://docs.oracle.com/javame/dev-tools/lwuit-1.5/devguide/portability.htm).

Кандидаты для изучения:

- **phoneME Feature.** Исторический проект с CLDC/MIDP и платформенными слоями; сохранился [архив исходников Sun](https://github.com/magicus/phoneME). Нужно выбрать именно подходящую конфигурацию, разобраться со старой сборкой, переносимым интерпретатором, endian/ABI и зависимостями. Порт с ARM/Linux или Android не равен порту на ARM7 с RTOS.
- **SquirrelJME / NanoCoat.** [Разработчики описывают C-движок NanoCoat](https://github.com/SquirrelJME/SquirrelJME), способный работать без установленной host JVM. Это кандидат для оценки. Пригодность конкретной конфигурации к SC6600L, big-endian и доступной памяти не проверена; потребуется измерение и порт платформенного слоя.
- **Маленькая собственная VM.** Подходит как учебный эксперимент и для первого байткода, но совместимые библиотеки и корректность GC/потоков быстро становятся большим проектом.

**FreeJ2ME/FreeJ2ME-Plus** полезен как эталон поведения игры на Windows. Он сам опирается на Java VM; [так прямо описывает проект его разработчик](https://github.com/TASEmulators/freej2me-plus). Копирование `freej2me.jar` в flash B220 не создаст недостающую JVM. Он также не исполняет штатную прошивку Explay.

Рекомендуемая лестница проверки: арифметика и методы → объекты/GC/исключения → простая графика → клавиши и repaint → один заранее выбранный MIDlet → RMS и изображения → библиотека небольших игр → звук и расширения. Первые шаги выполнять на Windows с той же VM и собственной HAL, затем на RAM-программе телефона. Это позволяет продвигаться к Java независимо от готовности полного эмулятора штатной ОС.

Нативная VM внутри штатной системы сохранит потенциальный доступ к её файловым и графическим функциям, но потребует точного ABI и осторожной интеграции с планировщиком. Отдельная среда, загружаемая вместо ОС, проще по зависимостям, однако телефонные функции в ней придётся реализовывать заново либо не включать. Это важный выбор архитектуры, который имеет смысл делать после первых измерений RAM и рабочего вывода на экран.

## 12. Как продолжать реверс в Ghidra

Импортировать **извлечённый PS**, не PAC, как raw binary:

```text
Language: ARM:BE:32:v4t
Image base: 00000000
Reset: 006A4228, ARM
```

Идентификатор языка подтверждается [официальным ARM.ldefs Ghidra](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/ARM/data/languages/ARM.ldefs). Выбор compiler spec/ABI следует уточнить по реальным вызовам, а не только по возрасту файла.

Далее:

1. Разметить векторы как ARM-команды, значения `0x20...0x3F` как указатели.
2. Перейти на Reset и реальный runtime handoff, не дизассемблировать целиком картинки/таблицы.
3. Добавить блок RAM около `0x04000000` и SRAM около `0x40000000`, перенести два инициализируемых участка из таблицы. Отдельно отметить подтверждённые BSS-области.
4. Для известных Thumb-входов установить контекст TMode=1; учитывать младший бит указателей функций и ARM-переходники.
5. Проставить строки ASCII/UTF-16BE и ссылки на диагностические сообщения, затем именовать функции по доказательствам.
6. Найти функции файловой системы, выделения памяти, рисования, MMI-событий и таймеров. Не импортировать произвольные заголовки другой версии SDK как точные структуры.

FDL импортировать отдельной программой с той же endian/ISA и базой `0x34000000`. При анализе кода, который копируется в SRAM, учитывать runtime-адреса его функций, а не только положение байтов в исходном FDL. Символов отладчика/исходной карты линковки в пакете не найдено.

Ghidra в этой сессии не запускалась: выполнены Capstone-дизассемблирование и Unicorn-пробы. Приведённые инструкции — подготовленная процедура следующего этапа, не отчёт об уже проведённой декомпиляции всего образа.

## 13. Практическая последовательность работ

| Этап | Проверяемый результат |
|---|---|
| 0. База исследования | Выполнено: распаковка, хеши, ресурсы, карта старта, пробы исполнения |
| 1. Сервисный readback | Два одинаковых полных дампа телефона; определены физическая flash, Boot ROM/FDL и bootkey |
| 2. RAM hello | Свой небольшой бинарник выполняется без записи новой прошивки и даёт наблюдаемый результат |
| 3. Экран и клавиши | Собственная тестовая графика 176×220 и события клавиатуры на устройстве |
| 4. Минимальный ABI | Проверенные вызовы LCD, файлов, памяти и таймеров либо собственные драйверы |
| 5. Первый постоянный патч | Воспроизводимо добавленная функция меню с возвратом в штатный интерфейс |
| 6. Windows-стенд | Реальная обработка критичных MMIO, IRQ, LCD; boot штатного MMI без полноценного радио |
| 7. Java proof of concept | Выбранная VM исполняет тесты на Windows и ARM, измерены heap и скорость |
| 8. J2ME | Запуск выбранного MIDlet, потом расширение поддерживаемых API |

Этапы 2–4 и 6 могут развиваться независимо. Делать полностью точный эмулятор обязательным условием первого RAM hello неоптимально по объёму реконструкции. Но Windows-стенд полезен с самого начала для трасс, отдельных функций и проверки машинного кода.

Сейчас не установлены: точный чип и ревизия на плате, flash ID/геометрия, bootkey, USB-поведение, карта индивидуальных NV, выбранный LCD, таймеры/IRQ, полный ABI, доступный heap, возможность загрузки произвольного неподписанного блока. Эти пункты нельзя честно закрыть одним разбором дистрибутивного PAC.

## 14. Воспроизведение и состав результатов

Подготовлены Python 3.13 и локальная `.venv` с Capstone 5.0.9, Unicorn 2.1.4, Pillow 11.0.0. Исходный ZIP и распакованная прошивка не изменены. Драйверы не устанавливались, устройство не прошивалось.

Полный повтор офлайн-анализа в текущей папке:

```powershell
.\run_analysis.ps1
```

Для нового окружения сначала:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-analysis.txt
```

Отдельные команды:

```powershell
.\.venv\Scripts\python.exe tools/analyze_firmware.py
.\.venv\Scripts\python.exe tools/carve_resources.py

.\.venv\Scripts\python.exe tools/inspect_code.py --offset 0x59d888 --size 0x4e --thumb
.\.venv\Scripts\python.exe tools/verify_artifacts.py
```

Проверка подтверждает целостность и воспроизводимость указанных артефактов. Она не подменяет испытания на телефоне и не подтверждает ещё не сделанные патчи.
