# Эмуляция B220: DSP bootstrap, IRQ и запуск MMI

**Этот отчёт описывает этап до реализации JPEG. Актуальный результат —
[домашний экран, JPEG и ускорение](JPEG_PROGRESS_RU.md).**

Актуально на 1 ноября 2026 года. Работа выполняется без телефона, исходный PS
не патчится. Эмулятор продвинулся за прежнее ожидание DSP: работает планировщик
RTOS, создаются задачи интерфейса MMI, читаются часы и записываются настройки.
Получены три полных кадра штатной анимации EXPLAY. Следующий установленный
рубеж — аппаратный JPEG-декодер: прошивка обращается к его регистрам, модели пока нет.
**Первый экран меню и управление клавишами пока не получены.**

![Кадр заставки после исправления геометрии NOR](analysis/emulator/31-nor-parameter-blocks-lcd.png)

## Как запускать сейчас

Двойной щелчок по `Explay B220.lnk` или `Start B220.cmd`. Если открыто старое
окно от предыдущей версии, закройте его и запустите ярлык снова.

Окно теперь получает кадры во время выполнения: после каждой LCD DMA-передачи
эмулятор атомарно обновляет PNG, а окно подхватывает его. Экран не нужно ждать
до завершения всего прогона. Первый кадр — прежняя заставка, последующие зависят
от достигнутого этапа. Это не гарантирует непрерывную анимацию с реальной частотой.

Исправлен сбой `PermissionError / WinError 5` при замене живого PNG в Windows.
Окно копирует файл в память и закрывает его до загрузки в GDI+. Запись PNG
повторяется при краткой блокировке; если файл остаётся занят, пропускается только
обновление предпросмотра, исполнение прошивки продолжается. Счётчики публикаций
и пропусков, последняя ошибка доступны в JSON как `live_frame_output`.
Финальный кадр по-прежнему сохраняется отдельно после прогона.

Пробный запуск ограничен 180 секундами/200 млн инструкций. Первичная настройка
прошивки выполняет очень много словных записей NOR и пока работает медленно.
После паузы по лимиту окно сохраняет виртуальную NOR в
`analysis/emulator/window-nor-v2.bin` и использует её при следующем запуске.
Сохраняются NV и файлы телефона; CPU и RAM начинают загрузку заново.
Закрытие окна во время выполнения прерывает процесс: новые изменения попадут
в снимок только после штатного окончания прогона, предыдущий снимок сохранится.

Для текущего окна подготовлен начальный снимок из проверенного прогона
`31-nor-parameter-blocks.json`. Файл `.provenance.json` рядом фиксирует источник
и SHA-256; существующий снимок при такой подготовке не перезаписывается.
Это состояние виртуальной flash после работы прошивки, не дамп настоящего телефона.

Для старта с заводского шаблона закройте окно и переименуйте `window-nor-v2.bin`.
Этот файл относится только к виртуальному телефону. Исходные ZIP/PAC/PS/NV
из распакованного архива не изменяются.

Из консоли:

```powershell
# Текущий пробный запуск
.\run_emulator.ps1

# Прежний короткий рубеж перед первым ожиданием DSP
.\run_emulator.ps1 -BootOnly

# Произвольный запуск с отдельным снимком flash
.\.venv\Scripts\python.exe -m emulator.run --explore --instructions 100000000 --seconds 90 --save-flash analysis/emulator/my-nor.bin --live-frame analysis/emulator/my-live.png --out analysis/emulator/my-run.json

# Повторная загрузка с этим снимком
.\.venv\Scripts\python.exe -m emulator.run --explore --instructions 100000000 --seconds 90 --load-flash analysis/emulator/my-nor.bin --save-flash analysis/emulator/my-nor.bin --out analysis/emulator/my-next-run.json
```

В примерах с отдельным снимком лимит выбран вручную. Для длинного прогона можно
увеличить `--seconds`/`--instructions`. Повторный запуск тоже выполняет записи
настроек: сохранение flash пока не гарантирует быструю загрузку.

`-ContinuePastDspWait` сохранён для совместимости, но продолжение теперь является
обычным режимом. Для остановки по адресу остаётся `--until 0x...`.
Снимок NOR принимается только при размере 8 MiB и полном совпадении префикса PS
с закреплённой прошивкой. Это не снимок CPU, RAM или состояния периферии.

## Что восстановлено

| Узел | Наблюдение и реализация |
|---|---|
| DSP bootstrap | Mailbox `0x10000000`: command, status, word offset/count, буфер с +8. Приняты восемь блоков по 1024 слова — 16 KiB с PS `0x3e6c9c` |
| IRQ controller | Маскированный/raw status `0x80000000/04`, enable-set `+08`, enable-clear `+0c`. Чтение DIS даёт 0, а не маску EN |
| ARM IRQ entry | Переход через вектор `0x18`, banked SP/LR, SPSR, сброс T, установка I; возврат исполняет гостевой код |
| DSP completion | Каждый блок поднимает IRQ 13. Гостевой callback `0x526a26` сам выставляет флаг `0x0434c3dc` и подтверждает источник через `0x8b000014` |
| Countdown timers | Окна `0x81000000` и `0x81000020`, LOAD/VALUE/CTL/INT. Преобразование 32768 Hz установлено по `0x484d08`; timer IRQ 4 обеспечивает работу задач/таймаутов |
| RTC | Время `0x89000000..0c`, shadow `+10..1c`, alarm shadow `+20..2c`, enable `+30`, status `+34`, W1C `+38`. Подтверждения записи через IRQ 7 |
| RTC validity | Ветка `0x18e712` пишет bit19 в `0x8b000020`, а следующая проверка `0x18e6ea` ожидает bit17. Добавлен предполагаемый аппаратный side effect |
| SPI | Контроллеры `0x8e000000` и `0x8e003000`: ready/busy, RX count/FIFO, завершение тактирования. MISO читается высоким; SD отсутствует, внешний SIM switch не исполняется |
| EMC idle | Bit2 в `0x20000008` позволяет гостевому SRAM-коду пройти ожидание готовности шины перед переключением частоты. В модели передачи завершаются мгновенно |
| RTOS inspection | Отчёт читает кольцо `THRD` с `0x042b51d8`: имена, приоритеты, состояния, счётчики запусков, saved PC/SP и образцы стека. Это наблюдение, не вмешательство в планировщик |

SHA-256 реально переданного bootstrap-потока:
`31499aae94fa5b1b423def27d24254c0fa4a17315b7ed152e8c43e65a47d91cb`.
CLI сохраняет его рядом с отчётом как `*-dsp-bootstrap.bin`.
Он побайтно совпадает с соответствующим диапазоном исходного PS.

Это **модель протокола загрузчика**, а не эмуляция инструкций самого DSP.
Полноценного радио, DSP runtime-сервисов, SIM-карт, FIQ и всех DMA-каналов ещё нет.
RTC в окне идёт по местному времени компьютера (`emulator/rtc.py`): прерывания
минуты, часа, суток и будильника поднимаются на границах счётчиков (бит 1 →
сообщение `0x74` → сигнал `0x902` в MMI, часы перерисовываются). Заводской сброс
на 01.01.2012 (загрузка `0x17e75c`, MMI `0x1cee90`) игнорируется; время,
выставленное в настройках, хранится как смещение от часов компьютера до конца
сессии. В консольных прогонах время остаётся детерминированным.
Виртуальное время детерминировано числом входов в блоки CPU; реальная частота
кварца, скорость SoC и тайминги шины не воспроизводятся.

## Почему пришлось изменить причину старта

Прежнее `0x8b000020 = 1` помогло добраться до заставки, однако позднее выяснилось,
что `0x17e11c..0x17e124` выбирает для него специальную ветку Layer1.
Обычная процедура `POWER_PowerOn` обходилась, поэтому задачи MMI не создавались.

Текущий профиль задаёт значение `4`: оно проходит общую ветку `0x17e138`,
выполняет `POWER_PowerOn` и запускает `T_P_APP`, задачи SIM и другие службы.
Это выбор поддерживаемого пути исполнения по коду, а не измерение регистра
на настоящем телефоне. Физическое название причины `4` пока не установлено.

## Подтверждённое поведение

В реальном выполнении появились, в частности:

```text
POWER_PowerOn !!!
CHNG_FREQ task entry !
APP_Task: begin init
mmi_modu_main.c enter MMI_InitilizeWinIdNameArr()
[RES]: MMIRES_LoadComResource
MMK_StartApplet
main_app_init:call_ring_type
PlayPowerOnOffMP4:is_power_on
MMK_CreateWinTimer
```

Вместо assertion в SPI guest делает попытки CMD0 и штатно сообщает об отсутствии
карты. Задачи SIM проходят свои таймауты и сообщают `SIM Not Ready`.
После исправления RTC прошло прежнее бесконечное ожидание записи времени,
затем проверка корректности времени и создание остальных настроек MMI.

В свежем запуске с исправленной геометрией NOR получены три полных кадра через
12 DMA-передач, суммарно 116 160 записей пикселя. Последний кадр визуально проверен:
это следующий этап заставки. Цветопередача/BGR и ориентация на физической панели
ещё не сверены.

## Текущая остановка: JPEG

Прогон `31-nor-parameter-blocks.json` доходит до записи значения `9` в
`0x20200000` из Thumb-кода `0x5e118c`, функция начинается с `0x5e1188`.
Этот же участок программирует буферы `0x20200040..5c` и таблицы с `0x20210000`.
Рядом находятся обработка JPEG SOF0, размеров, субдискретизации YUV и таблиц
квантования/Хаффмана, строки Baseline/Progressive. Это основание для определения
устройства; точной документации блока и полной карты регистров пока нет.

Окно показывает отдельную причину остановки — «аппаратный JPEG-декодер».
Диапазон `0x20200000..0x2021ffff` не возвращает фиктивное завершение: обращение
останавливает исполнение с адресом, PC и значением в отчёте. Следующий этап —
восстановить входные/выходные буферы и формат аппаратного результата, затем
реализовать декодирование с корректным завершением операции и IRQ, если его
ожидает драйвер. Одного пропуска вызова недостаточно для правильного изображения.

Повторный прогон `33-jpeg-boundary.json` с сохранённой NOR воспроизводит ту же
запись и уже показывает причину `unimplemented peripheral`, устройство `JPEG engine`.
Он занял около 109 секунд на текущем компьютере и снова вывел три кадра.
Поле `engine_error` содержит `UC_ERR_WRITE_UNMAPPED`: JPEG-окно специально
остаётся незамапленным до реализации модели, поэтому это ожидаемый рубеж стенда.

## Отчёты и диагностика

**Поправка к геометрии flash:** поздняя трасса обнаружила восемь физических
8-KiB parameter blocks в последнем участке `0x7f0000..0x7fffff`.
Прежний вывод о равномерных 64-KiB блоках был верен для логической EFS,
но неверен для физического стирания этого участка. Модель исправлена:
стирание `0x7fe000` теперь сохраняет соседние `0x7f0000..0x7fdfff`.
Тест отдельно проверяет эту границу. Добавлена наблюдаемая команда B0:
при мгновенно завершённом стирании она возвращает ready, а не изображает
незавершённую операцию; последующий resume D0 не стирает данные повторно.

Снимки `research-nor*.bin` и отчёты до `30-extended-warm` включительно
относятся к прежней геометрии. Они сохранены как история исследования,
но не являются чистым исходным состоянием для нового теста.
Новая серия начинается с пустой EFS в `31-nor-parameter-blocks.json`;
её снимки находятся в `analysis/emulator/nor-v2/`. Окно использует отдельное
имя `window-nor-v2.bin`, чтобы автоматически не загрузить старую память.

- `18-dsp-protocol.json`: пройден bootstrap, восемь IRQ 13, запуск RTOS.
- `19-timer-irqs.json`: работа таймерных IRQ, прежний SPI assertion.
- `20-spi-no-card.json`, `21-emc-idle.json`: протокол отсутствующей SD и idle-путь.
- `22-normal-boot.json`, `23-sim-spi.json`: обычное включение, создание MMI.
- `26-rtc-irq.json`: обработчик RTC работает, но ещё отсутствовал validity side effect.
- `27-rtc-valid.json`: проверка времени пройдена, настройка остальных модулей.
- [Свежая flash, исправленная геометрия, выход на JPEG](analysis/emulator/31-nor-parameter-blocks.html).
- [Повторная загрузка: подтверждённая остановка на JPEG](analysis/emulator/33-jpeg-boundary.html).
- Отчёты `28-extended-boot` и `29-warm-start` — история до исправления геометрии.

Новые JSON содержат точное `nor_event_count`, но по умолчанию хранят только
первые и последние 4096 команд NOR. Поле `nor_events_truncated` явно показывает
усечение. Для полной трассы задайте `--full-nor-trace`; длительная первичная
настройка может создать сотни тысяч записей. Содержимое flash можно исследовать
отдельно через `--save-flash`, не восстанавливая его из выборки команд.

## Следующая работа

1. Восстановить модель JPEG: регистры, входной поток, выходной формат, завершение
   и необходимые прерывания. Затем проверить дальнейшую загрузку до обычного экрана.
2. Ускорить исполнение без подмены результатов функций и без отключения проверок
   гостя. Сохранение flash уже позволяет не начинать каждое исследование с пустой EFS.
3. Восстановить недостающие DSP runtime/FIQ/DMA события, если до них дойдёт UI.
4. После первого обычного экрана — клавиатурная матрица и повторяемый ввод.

Проверки: `python -m unittest discover -s tests -v` в локальном `.venv`: 28 тестов, PASS.
Они включают настоящий запуск PS до MMI/RTC, точные DSP-байты, реальные IRQ
прошивки, сохранность соседних 8-KiB блоков NOR и отдельный тест сохранности
ARM/Thumb-состояния при IRQ/return. Неизвестный JPEG отдельно проверяется на
явную остановку вместо молчаливого подтверждения.
Регрессия живого экрана проверяется настоящим Win32-дескриптором без
`FILE_SHARE_DELETE`: CPU должен завершить LCD DMA при заблокированном PNG,
а после освобождения файла публикация должна возобновиться.
Синтетический вектор используется только в изолированном unit-тесте;
в настоящем запуске и исходных файлах инструкции не заменяются.
