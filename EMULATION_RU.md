# Эмуляция Explay B220: заставка уже работает

**Текущий статус на 1 ноября:** пройдены DSP bootstrap и IRQ, запущена MMI,
добавлены RTC и сохранение flash; получен следующий кадр заставки.
[Актуальная инструкция, результаты и ограничения](EMULATION_PROGRESS_RU.md).

Ниже сохранено описание первого этапа от 31 октября; его прежняя остановка
на DSP и старые параметры запуска больше не описывают текущий полный режим.

31 октября 2026 года. Работа выполнена без телефона, по имеющемуся PAC.

**Оригинальная прошивка выполняется в Windows до вывода заставки EXPLAY.**
Получен кадр 176 × 220 через модели LCD и DMA. Затем выполнение доходит до
ожидания ответа DSP. Меню, кнопки и работа приложений пока не реализованы.

![Кадр, сформированный прошивкой через виртуальный LCD](analysis/emulator/boot-to-dsp-lcd.png)

Это выполнение ARM/Thumb-кода из PS: прошивка распознаёт виртуальную память,
создаёт файловую систему, читает NV, выбирает драйвер панели, выводит изображение
и печатает свои отладочные сообщения. Картинка не подставляется из извлечённого
ранее GIF. Исходный PS не патчится; аппаратные ответы задаются в модели платы.
Тест сравнивает все байты PS в памяти после загрузки с исходным файлом.

Большая часть периферии ещё представлена предположениями. Результат подтверждает
конкретный путь загрузки в исследовательской модели. Соответствие поведения
настоящему телефону предстоит проверить отдельно.

## Запуск

### Окно с экраном

Дважды щёлкните **`Explay B220.lnk`** в корне проекта. Окно открывается сразу,
запускает эмулятор в фоне и по окончании загрузки показывает полученный LCD-кадр.
Доступны выбор масштаба, перезапуск, сохранение PNG в исходном разрешении
176 × 220 и просмотр журнала. Закрытие окна останавливает текущий запуск.

Если папку переносили, используйте **`Start B220.cmd`**: он находит проект
относительно себя. Ярлык привязан к текущему пути папки.
Устанавливать дополнительные библиотеки для окна не требуется: оно использует
Windows Forms, а эмулятор — подготовленное окружение `.venv`.

Это пока просмотр кадра после загрузки до DSP, не непрерывное обновление LCD
во время исполнения. Статус под экраном объясняет, почему заставка остаётся
неподвижной. Меню и клавиатура ещё не работают.

Код окна: `emulator/window.ps1`. Его текущие результаты сохраняются отдельно
как `analysis/emulator/window-latest.*`; исходные компоненты прошивки не меняются.

### Консоль и отчёты

В подготовленной папке:

```powershell
.\run_emulator.ps1
```

Скрипт останавливается перед первым ожиданием DSP, PC `0x526912`.
Контрольный запуск занял около 5,2 секунды; скорость зависит от ПК.

- [HTML: экран и журнал прошивки](analysis/emulator/boot-to-dsp.html).
- [JSON: полный отчёт, MMIO, NOR, регистры и блоки кода](analysis/emulator/boot-to-dsp.json).
- [PNG виртуального LCD](analysis/emulator/boot-to-dsp-lcd.png).
- `analysis/emulator/boot-to-dsp-lcd.rgb565be`: 77 440 байт GRAM.

HTML открывается обычным браузером. Это просмотр результата запуска,
не интерактивный интерфейс телефона. Программа работает офлайн, без USB.

Прямая команда и режим продолжения:

```powershell
.\.venv\Scripts\python.exe -m emulator.run --explore --until 0x526912 --out analysis/emulator/boot-to-dsp.json
.\run_emulator.ps1 -ContinuePastDspWait
```

Продолжение сейчас приводит к циклу ожидания DSP; результат сохраняется отдельно
в `analysis/emulator/explore-budget.json`. По умолчанию ограничение составляет
12 млн инструкций или 20 секунд, что наступит раньше. Число инструкций — бюджет,
а не измеренный результат; отдельно считаются входы в транслируемые блоки.
Доступны параметры `--instructions`, `--seconds`, `--until`, `--profile`, `--out`.

Строгий режим:

```powershell
.\run_emulator.ps1 -Strict
```

Он останавливается на первом неизвестном MMIO: запись `0x4ff7ffff` в
`0x8000000c`, PC `0x6a4238`. В `--explore` неизвестные MMIO разрешены как
нулевая память с сохранением записей. Все обращения видны в отчёте: в контрольном
запуске до DSP таких обращений было 9331. Успешный explore-запуск ещё не означает
полную аппаратную эмуляцию.

При переносе проекта на другой Windows-ПК:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-analysis.txt
```

Проверено с Python 3.13, Unicorn 2.1.4, Capstone 5.0.9, Pillow 11.0.0.
Нужны компоненты `analysis/extracted/*`; их создаёт `run_analysis.ps1`.

## Подтверждённый путь загрузки

| Этап | Наблюдение |
|---|---|
| Reset | Вектор 0 → `0x6a4228`, копирование/очистка RAM и SRAM |

| Внешняя память | Проходят `-- EMC_Init (+) --` и `-- EMC_Init (-) --` |
| DMA, файловая система, NV | Проходят `DMA_HalInit`, `EFS_Init`, `REFPARAM_InitRefParam` |
| LCD | Драйвер читает `0x9225`, выбирает первую из девяти записей таблицы, вызывает `ILI9225_Init` |
| Питание/калибровки | Проходят `PROD_InitProdParam`, `PROD_Init`, настройка зарядного менеджера |
| Изображение | Четыре DMA-передачи: 77 440 байт → 38 720 RGB565-пикселей |
| Версии | `MOCOR_09A.W10.25.16.04_Debug`, `SC6600L_sp6601l_trisim`, `BASE_10A.W11.24.02`, `7-20-2012 9:59:54` |
| Ожидание | Полусловное чтение `0x10000002`, ожидание бита 0 в `0x526912` |

Контрольный запуск дал 80 сообщений, 4231 запись команды NOR, 685 программирований
полуслова и 12 стираний сектора. Изменения flash остаются в RAM процесса.
Каждый запуск начинает с исходного PS, release NV и пустой оставшейся flash;
сохранения состояния между запусками ещё нет.

## Реализованная модель и её границы

Код: [emulator/board.py](emulator/board.py), профиль:
[emulator/profiles/b220-l7a.json](emulator/profiles/b220-l7a.json).
Рядом с существенными предположениями в профиле записаны основания.

| Узел | Реализовано | Ограничение |
|---|---|---|
| CPU | ARM/Thumb BE через Unicorn | ARM926 как приближение к предполагаемому ARM7TDMI; точность всех инструкций/исключений не установлена |
| Endian | BE-код/данные, проверка CPSR.E на границе блоков | Адаптер совместимости с фиксированным BE; в контрольном запуске исправлений E не потребовалось |
| NOR | 8 MiB от 0; PS длиной 0x7452fc защищён от program/erase | ID `0x20/0x88c0` выбран из поддерживаемой таблицы; реальная микросхема неизвестна |
| RAM | 4 MiB от `0x04000000`, общий backing с `0x34000000` | Ёмкость и alias пока гипотезы |
| SRAM | 64 KiB от `0x40000000` | Размер окна не измерен на устройстве |
| DSP shared memory | 4 KiB от `0x10000000` | Только хранилище; нет DSP и ответов mailbox |
| System counter | `0x81003004`, enable bit 3 в `0x81003008` | 1 тик = 1 мс времени гостя; время считается по инструкциям (см. «Скорость и время») |
| DMA gate | request bit 0 / ack bit 2 в `0x20100000` | Мгновенное подтверждение, не весь DMA |
| LCD DMA | Наблюдаемая линейная передача канала 16 в LCD | Только config `0x04880160`, stride `0x20000`, frame `2`; мгновенное завершение, без IRQ |
| LCD | Частичная ILI9225: ID, окна, курсор, GRAM, 8-битная шина | Выбрана поддерживаемая панель; физическая неизвестна. Нет analog/gamma/scan timing |
| ADC | Выбор канала, start, ready, результат | Канал 5 возвращает 900, остальные 0; мгновенное преобразование |
| Прочие MMIO | Explore-хранилище | Нет аппаратных side effects, событий и достоверной W1C-семантики |

Регистры LCD и движение по GRAM сверены с
[драйвером ILI9225 в Linux](https://raw.githubusercontent.com/torvalds/linux/master/drivers/gpu/drm/tiny/ili9225.c).
Адреса шин, байтовая полоса и чтение ID установлены по самой прошивке.

Два выбранных стартовых значения: `0x8b000024 = 0x000d0078` — принимаемая кодом
конфигурация PLL; `0x8b000020 = 1` — причина старта для текущего пути с release NV.
При нулевой причине старта с этими NV код уходит в ранний power/reset-путь.
Это не измеренные значения настоящего B220.

ADC установлен по цепочке `0x492626` → `0x17c16c`: канал 5, start bit 1,
ready bit 6, результат в младших десяти битах `0x8a00300c`. Значение 900 —
выбранный виртуальный исправный аккумулятор, не аппаратное измерение.
Без модели ADC прошивка читала 0 и сама вызывала `POWER_PowerOff !!!`.

## Скорость и время

Главное правило: **эмулятор не должен работать быстрее настоящего телефона.**

* **Время гостя считается по инструкциям.** В профиле (`"cpu"`) задано
  `instructions_per_ms` = 20 000 — гость получает 20 млн инструкций на секунду своего
  времени. От этого времени идут таймеры, RTC, счётчик `0x81003004` и кадры.
* **Почему 20 000.** Настоящий процессор (ARM926EJ-S, SC6600L) быстрее, предположительно
  80–100 МГц, но на телефоне это ещё не измерено. Поэтому число взято заведомо ниже.
  Когда телефон будет доступен, `BENCH.GO1` ([apps/card_bench.c](apps/card_bench.c))
  нужно запустить на нём и в эмуляторе. Отношение результатов даст поправку
  к `instructions_per_ms`.
* **Срезы.** CPU исполняется срезами по 0,5 мс, без Python-хука на каждый блок.
  Прерывания, клавиатура, таймеры и RTC обслуживаются между срезами. NOR в режиме
  команд перехватывается только на странице команд и в области настроек.
* **Ожидания.** Каждое чтение MMIO засчитывается как 16 инструкций. Если в срезе больше
  четырёх чтений счётчика или таймера, это цикл ожидания: срез заканчивается, и время
  засчитывается целым срезом. С выключенными IRQ так делается, только пока нет
  ожидающего прерывания и не наступило событие таймера. Иначе процедура сна в простое
  (она читает счётчики с маской IRQ) заканчивала бы каждый срез внутри маски,
  и прерывания не доходили бы никогда.
* **Простой.** В прошивке нет WFI: сон — последовательность регистров питания, на которой
  эмулятор не останавливается. Поэтому вход в сон задачи простоя (PS `0x495dda`,
  `idle_entry` в профиле) переводит время гостя к следующему событию таймера, не больше
  10 мс за раз. На этом входе IRQ открыты, а сразу после него маскируются. Поэтому
  ожидающее прерывание берётся прямо там, как его взял бы процессор. Раньше оно ждало
  конца среза, который почти никогда не попадал в это окно. В списке «Приложения»
  из-за этого было 14 000 попыток сна в секунду гостя и 0,13 секунды гостя за секунду
  на ПК, а стало около 9,5.
* **Регулятор окна.** В окне гость не обгоняет настенные часы: если время гостя ушло
  вперёд, окно ждёт. Отставание (медленный ПК, пауза) не догоняется.
  Каждый запуск окна ограничен и инструкциями, и временем гостя.
* Ожидания и простой дают гостю время без работы. Значит, инструкций на миллисекунду
  становится только меньше, не больше.

Скорость на ПК разработки:
- примерно 20 млн инструкций гостя в секунду при счёте;
- около 0,8–0,95 секунды гостя за секунду на загрузке и в меню;
- в простое регулятор держит реальное время.

Было: Python-хук на каждый блок, около 0,5 млн инструкций в секунду. Без профиля `"cpu"`
работает этот старый режим (1 блок = 1/128 мс).

## Геометрия NOR и release NV

Выбранная гостем запись геометрии с PS `0x2f8` даёт:

| Адреса | Назначение |
|---|---|
| `0x7a0000..0x7a3fff` | Первый fixed-NV слот 16 KiB |
| `0x7a4000..0x7a7fff` | Второй fixed-NV слот 16 KiB |
| `0x7b0000..0x7fffff` | EFS, пять секторов по 64 KiB |

`nvitem_release.bin` размером 0x3d1c помещается в слот. Его структура совместима
с BE-сканером `0x1816cc`: после четырёх байт заголовка идут выровненные записи
ID/длина/данные. Шаблон подставлен в обе виртуальные NV-области. Без него
`PROD_InitProdParam` доходит до assertion в `prod_param.c`.
Это заводской шаблон из PAC, не дамп реального телефона. Смысл и контрольная
сумма всех полей пока не восстановлены. PS и release NV закреплены SHA-256 в профиле.

NOR поддерживает наблюдаемые ID/unlock/config/reset/status-команды,
программирование слова и стирание сектора. Program меняет только 1 → 0;
попытка 0 → 1 даёт ошибку статуса. Операции мгновенные. Неподдерживаемая команда
останавливает запуск; исходные файлы на диске не изменяются.

## Откуда взялся кадр

1. Гостевая таблица `0x042ccef8` задаёт command port `0x08000000` и data port
   `0x08020000`. `_LCM_ReadID` (`0x6bd464`) получает `0x9200`, затем `0x2500`.
2. Инициализация программирует окно 176 × 220, направление и RGB565.
3. Код около `0x496638` заполняет DMA-дескриптор канала 16 в `0x20100600`.
   Источник начинается с `0x04280200`, приёмник фиксирован `0x08020000`.
4. Передаются `22528 + 22528 + 22528 + 9856` байт через виртуальную 8-битную
   шину LCD; курсор GRAM продвигается по заданному окну.

Без DMA-модели были четыре `_LCM_WaitDMADone: time out !!` и ноль пикселей.
С передачей таймауты исчезли, появился EXPLAY. Кадр проверен визуально.
PNG показывает прямую RGB565-интерпретацию GRAM. Точная цветопередача с учётом
BGR/подключения панели и ориентация относительно физического дисплея ещё не проверены.
SHA-256 сырой GRAM:
`a07f230ca92130efe570c6eca1ea0365392f3b34502c3e95e105097c7bede5c5`.

## Текущий барьер: DSP bootstrap

Увеличение бюджета не поможет: отсутствует сторона, которая должна отвечать.
Восстановленный ARM-протокол выглядит так; это наблюдения кода, не документация DSP:

| Адрес | Наблюдаемое использование |
|---|---|
| `0x10000000` | Host command/flags: 1, затем 3; далее OR с 4 и для последнего блока 8 |
| `0x10000002` | DSP status: ожидание битов 0, 1, 2 на разных этапах |
| `0x10000004` | Смещение блока в 16-битных словах, с readback |
| `0x10000006` | Число 16-битных слов блока, с readback |
| `0x10000008...` | Буфер блока, до 1024 слов |

`0x526a38` готовит канал и вызывает `0x5268f2`. В точке остановки:
R2=`0x10000000`, R5=`0x003e6c9c`, R1=`0x2000`. Длины и смещения считаются
в словах: `0x5267ea` удваивает их перед копированием. Текущий payload —
16 KiB с PS `0x3e6c9c`, порциями до 2 KiB.

`0x526912` ждёт status bit 0. После приёма блока код ждёт bit 1 около
`0x526836`, затем bit 2 около `0x5268d4`. После этого есть ожидание байтового
RAM-флага в `0x5268e2`, вероятно связанного с обработчиком прерывания;
его происхождение ещё нужно проследить. Постоянный status «всё готово»
не покрывает весь обмен.

## Ближайший план

Следующий полезный рубеж — пройти DSP-bootstrap и дойти до задач MMI/первого
экрана меню. Для этой работы телефон пока не нужен.

1. Найти обработчик события загрузчика и происхождение ожидаемого RAM-флага.
2. Сделать автомат mailbox: запрос, приём блока, подтверждение, завершение;
   сохранять загружаемые DSP-байты. Сначала моделировать протокол. Потребность
   в исполнении самих DSP-инструкций станет ясна по следующим вызовам.
3. Восстановить контроллер прерываний, доставку IRQ с ARM banked state и таймеры.
4. Выяснить минимальные ответы DSP/радиочасти для офлайн-UI. Пока неизвестно,
   насколько жёстко MMI ждёт эти сервисы.
5. После появления задач UI добавить клавиатурную матрицу и frontend с живым LCD.
6. Добавить снимки RAM/NOR/регистров, сохранение flash и повторяемый ввод для
   проверки патчей.

Сейчас конкретное зависание объясняется периферией, а не доказанной ошибкой CPU.
Поэтому менять backend ради этого ожидания рано. Если ограничения ARM926/ARM7
или сложность IRQ станут существенны, восстановленные устройства можно перенести
на другой backend, в том числе отдельную QEMU machine. Профиль и тесты при этом
останутся полезны.

Эмулятор поможет проверять патчи, но не гарантирует их корректность на устройстве.
Для J2ME отдельно понадобятся запуск своего нативного кода, API дисплея/ввода/файлов
и порт VM/CLDC/MIDP. Вывод заставки эти задачи ещё не решает.
