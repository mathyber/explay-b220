# Локальная HTTP-страница в штатном браузере B220

Предыдущий прототип сохранён коммитом `310d77a`. Следующий результат:
исходная прошивка отправляет HTTP-запрос на тестовый сервер Windows, получает
HTML и выводит его на своём экране. Нажатие OK на ссылке открывает следующую
страницу через новое соединение. Изменений файлов прошивки нет.

## Повторить

В этом рабочем каталоге подготовлен совместимый снимок редактора с адресом
`http://a.aa`. Запуск из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m tools.network_probe --load-state analysis/emulator/network/url-input/04-2.b220state --steps soft_left,ok,wait --instructions 5000000 --http-test --out analysis/emulator/network/my-http-test
```

Каталог `--out` должен быть новым или пустым. Прогон выполняется без оконного
интерфейса: после каждого шага сохраняется PNG. Здесь первый шаг подтверждает
URL, второй нажимает OK на выделенной ссылке `Next page`, третий даёт завершить
рисование. Если CPU остановился по лимиту времени до готовности страницы,
увеличьте бюджет `--seconds` и вставьте `wait` перед `ok`.

Подготовить исходный снимок из уже сохранённого редактора, в котором есть
только `http://`, можно так:

```powershell
.\.venv\Scripts\python.exe -m tools.network_probe --load-state analysis/emulator/network/06-url.b220state --steps 2,1,2,2 --instructions 4000000 --out analysis/emulator/network/my-url-input
```

Полученный `my-url-input/04-2.b220state` передайте в первую команду. Снимки
локальные и не входят в Git. Сам эксперимент создаёт только изображения и
журналы: состояние с активной HLE-сетью пока не сохраняется.

## Что получилось

На экране реального MMI-рендерера появляются `B220 NETWORK OK`, случайный код
вида `B220-096176`, адрес страницы и ссылка. Код генерирует сервер при каждом
запуске; он присутствует в ответе и на экране телефона.

Проверенный прогон находится в `analysis/emulator/network/http-links/`:

* `01-soft_left.png` — первая страница.
* `03-wait.png` — следующая страница с `Page: /next`.
* `http-server.json` — сервер получил `GET /` и `GET /next`, `Host: a.aa`.
* `host-network.json` — создание/подключение/передача/чтение/закрытие двух
  сокетов и первые 8192 байта запросов/ответов.
* `network-trace.json` — исходные CMS-вызовы и сообщения прошивки.
* `virtual-network.json` — подготовка RAM и штатное подтверждение PDP.

В этом прогоне телефон отправил 1542 байта HTTP и получил 666 байт. После
обоих ответов прошивка сама закрыла соединения. При обычном запуске без
лабораторных флагов никакой сетевой backend не включается.

## Как устроен путь

`--http-test` включает прежний эксперимент SIM1/PDP и отдельную сокетную HLE
в `emulator/host_network.py`. Сам `tools/http_fixture.py` запускает сервер на
`127.0.0.1` со свободным портом и останавливает его при завершении прогона.

DNS пока представляет собой явное лабораторное соответствие `a.aa → 127.0.0.1`.
Гостевой адрес `127.0.0.1:80` направляется на этот единственный порт сервера.
Другие имена, адреса и порты дают явную остановку. Системный DNS и внешние
сайты не используются; это проверка транспорта и браузера, а не общий доступ
к интернету.

Сохранены штатные CMS-адаптеры, таймеры опроса приёма, очереди сообщений,
HTTP-парсер, обработка ссылок и рисование. Подменяется нижний сокетный API:
данные передаются через настоящие TCP-сокеты Windows. Запросы HTTP строит
прошивка; тело ответа в RAM для отрисовки отдельно не вставляется.

Восстановленная часть ABI для этой PS:

| Вход Thumb | Вызов | Аргументы и результат |
|---|---|---|
| `0x2cfb32` | socket | `r0=2, r1=1, r2=0, r3=1`; положительный непрозрачный handle |
| `0x2cf9c6` | DNS | `r0=ASCII name`; указатель на big-endian hostent |
| `0x2cfb6e` | connect | handle, sockaddr, размер 16; family/port big-endian, IPv4 байтами |
| `0x2cfbca` | send | handle, buffer, length, flags=0; число реально отправленных байтов |
| `0x2cfbaa` | recv | handle, buffer, length, flags=0; байты, 0 для EOF, -1 при ожидании |
| `0x2cfc38` | ошибка | handle; код 6 при would-block, 13 при закрытии, 22 при незавершённом connect |
| `0x2cfc2c` | close | handle; закрытие соединения |
| `0x2cfb92` | ioctl | наблюдаемая команда `0x1014, 0`; принимается для сокета HLE, хостовый сокет работает без блокировки |

hostent содержит пять 32-битных полей: name, aliases, family, длина адреса,
указатель на список адресов. Размер IPv4 равен 4; список заканчивается нулём.
Структура лежит в отдельной отображённой странице `0x50000000`, удаляемой при
закрытии backend. Её формат проверен исходной функцией CMS, которая превратила
ответ в строку `127.0.0.1`.

Подключение/передача/приём не блокируют CPU на ожидании сокета. Неполная
передача возвращает фактический размер; отсутствие данных возвращает ошибку,
которую штатный таймер CMS обрабатывает повторным опросом. В режиме есть лимиты:
8 одновременных сокетов, 128 handles за сеанс, 1 МиБ общего трафика, 512 событий
в отчёте. Неизвестные наблюдаемые сокетные API останавливают эксперимент.

Проверки: полный набор из 78 тестов проходит. Сетевые тесты проверяют структуру
DNS исходным кодом CMS, настоящий обмен с сервером маленькими порциями,
would-block, EOF, закрытый handle и освобождение ресурсов. Отказ Winsock
проверяется подачей кода `10061`; запрещённые маршруты и неизвестные API
останавливаются до передачи данных. Исходные файлы и компоненты прошивки
прошли проверку неизменности. HTML и код сервера на PNG проверены визуально.

## Ограничения и следующий шаг

Это часть сокетной HLE для CMS, а не эмуляция сотового радиотракта или нативного
TCP/IP-интерфейса. SIM/регистрация подготовлены на уровне служб прошивки.
Сохранение живых соединений, полный жизненный цикл PDP, UDP, WAP1-шлюз и
подключение режима к обычному окну ещё требуют работы. Реальные DNS/HTTP уже
проверены отдельно; [отчёт о режиме `--internet`](INTERNET_RU.md).

При проверке внешнего сервера исправлен код would-block: исходный recv
возвращает 6, а 13 означает закрытие. На быстром локальном ответе прежняя ошибка
могла не проявляться; на внешнем сервере она приводила к преждевременному обрыву.
