# Первый нативный патч B220: перехват клавиши

**Проверено в эмуляторе:** изменённый PS загружается, настоящее событие KPD/IRQ
вызывает штатный обработчик, тот переходит в наш Thumb-код. Код записывает
`B220` в RAM, выполняет вытесненные инструкции и возвращается в штатный поток.
Обработчик возвращается вызывающей функции, интерфейс продолжает работу.
Перехват не требует изменений эмулятора или внедрения кода через Python.

## Запустить

Дважды щёлкните **`Start B220 MOD.cmd`**. Он воспроизводимо собирает образ из
оригинала и открывает обычное окно с экспериментальной прошивкой. По хешу
образа окно создаёт отдельные NOR и SD. Обычный `Start B220.cmd` запускает
оригинал.

Результат этого опыта — выполнение кода, надписи на экране ещё нет.
Чтобы увидеть выполнение:

1. Дождитесь интерфейса телефона.
2. Откройте **«Отладка…»**, задайте точку **`0x152f2e`** и нажмите «Применить».
3. Нажмите «Продолжить», закройте отладчик и нажмите экранную клавишу телефона
   (например, левую «Подтв.» в окне даты). Если экран уснул, сначала разбудите
   его; интересует событие, дошедшее до штатного обработчика.
4. При остановке откройте отладчик. PC будет `0x152f2e`, R0 — `0x42323230`.
   Скопируйте текущее значение **SP** в поле памяти и нажмите
   «Прочитать 128 Б». Первые четыре байта: **`42 32 32 30`**, то есть `B220`.
5. «Продолжить» завершает обработку клавиши. Точка останется активной и может
   сработать на следующем событии, включая отпускание клавиши. Пустое поле
   точек + «Применить» возвращает непрерывное исполнение.

Метка **временная**: она занимает локальную ячейку текущего стекового кадра.
После возврата из вставки исходная инструкция снова записывает туда ноль.
Постоянного глобального буфера этот патч не резервирует. В контрольном прогоне
SP в момент метки был `0x04052fac`; в другой сессии нужно читать фактический SP.

Можно выбрать образ вручную через «Прошивка…»:
`analysis/firmware-patches/key-marker/key-marker.bin`.
Сетевой HLE для изменённых образов отключён согласно правилам загрузчика.

## Что именно изменено

| Место | Изменение |
|---|---|
| `0x001a1236` | Исходный пролог `push {r3,r4,r5,lr}` сохранён |
| `0x001a1238–0x001a123b` | Две Thumb-инструкции заменены четырёхбайтным `BL 0x152f2a` |
| `0x00152f2a–0x00152f37` | Наш код и литерал, всего 14 байт |
| `0x001a123c` | Возврат к исходному `str r0,[sp]` |

Точная область вставки — **`0x00152f2a–0x00152f37` включительно**:
пять Thumb-1 инструкций (10 байт) и четырёхбайтный литерал `B220`.

```asm
ldr  r0, marker
str  r0, [sp]
; Здесь находится контрольная точка 0x152f2e.
lsls r5, r1, #16   ; первая вытесненная инструкция
movs r0, #0        ; вторая вытесненная инструкция
bx   lr           ; возврат в Thumb по 0x1a123c
```

Штатный пролог заранее выделяет 16 байт и сохраняет LR вызывающего кода.
Ячейка `[sp]` уже используется оригиналом как локальная переменная для
выходного указателя. Наш `BL` временно использует текущий LR; сохранённый LR
остаётся нетронутым. До следующего штатного вызова тело функции не читает LR.
Загрузка/запись метки не меняет флаги, а две воспроизведённые инструкции
восстанавливают ровно те значения R0, R5 и CPSR, которые получал оригинал.

### Откуда взялись 14 байт

Свободной областью случайную последовательность `FF` мы не объявляли.
В частности, найденные 4224 байта `FF` оказались внутри ABMP-картинки.

В JPEG-ресурсе по `0x0014c528` убран 18-байтный APP0/JFIF-сегмент.
Остальной JPEG, включая сжатые данные, сдвинут внутри **того же слота**
размером 27155 байт. Изображение после этого заканчивается раньше; код
помещён в хвост **после EOI**, а не поверх сжатых пикселей. Длина PS,
адрес начала ресурса, его внешняя длина и соседние ресурсы сохранены.
Сравнение декодированных RGB-пикселей через Pillow/libjpeg совпало побайтно.
Из-за сдвига JPEG суммарно изменились 26909 байт PS: исполняемая вставка мала,
но двоичный diff ресурса занимает почти весь его слот.

Это специально освобождённые 18 байт метаданных, а не найденный запас flash
для больших программ. Для следующего payload потребуется другой объём.
Открытие именно этого изменённого ресурса штатным просмотрщиком отдельно
пока не проверялось; полный прогон загрузки проверил другой JPEG-путь,
используемый заставкой.

## Воспроизвести сборку и проверку

```powershell
.\.venv\Scripts\python.exe -m tools.build_key_marker
.\.venv\Scripts\python.exe -m unittest tests.test_firmware_patch -v
.\.venv\Scripts\python.exe -m tools.prove_key_marker --original
.\.venv\Scripts\python.exe -m tools.prove_key_marker
.\.venv\Scripts\python.exe -m tools.prove_key_marker --compare
```

Сборщик принимает только оригинальный SHA-256, проверяет байты обработчика
и JPEG, границы вставки, дальность/декодирование BL и равенство пикселей.
Повторная сборка даёт тот же образ. Применение к уже изменённому PS отклоняется.

- [Сборщик](tools/build_key_marker.py) — проверка входа, вставка и манифест.
- [Ассемблерное описание](patches/key_marker.S) — пять инструкций и литерал.
  Пока сборщик записывает проверенные кодировки непосредственно: `.S` описывает
  их, отдельный ARM-ассемблер автоматически не вызывается.
- [Проверка на работающей прошивке](tools/prove_key_marker.py) — настоящие
  клавиши KPD, точки останова, чтение состояния и сравнение с оригиналом.

В проверочном инструменте нет записи в CPU/RAM через `mem_write`/`reg_write`:
наш код попадает в CPU только из собранного PS. При желании раннюю загрузку
можно продолжить из подходящего публичного `.b220state` через `--load-state`;
это проверяемое восстановление того же PS, не перенос состояния между образами.

## Результаты первого прогона

Сборка: **2 ноября 2026 года**, SHA-256 изменённого PS:
`a8210c1bcbe5681f743afb9da15da46c9efba688aa2e1e66e6a2b07e71eb6d5a`.

- Оригинал: независимая холодная загрузка и обработка левой экранной клавиши — PASS.
- Патч: загрузка из снимка ранней инициализации **этого же изменённого образа**,
  затем штатная обработка клавиши — PASS.
- Реальные аргументы обработчика: R0=`0x15`, R1=`0x201`, R2=`0x8`;
  Thumb, SVC, не IRQ-контекст.
- Метка `42323230` записана по `0x04052fac` при PC=`0x152f2e`.
- Сохранённый LR вызывающего кода — `0x0019b4f1`; обработчик вернулся
  по `0x0019b4f0` с прежним SP и R4–R11.
- Все проверенные регистры на входе и после полного возврата совпали
  между двумя прогонами. Начальные экраны и операции JPEG заставки совпали.
- После возврата оба образа сформировали следующий кадр, окно настройки времени.
  Поздние скриншоты снимаются после исполнения по лимиту реального времени;
  фаза мигающего курсора может различаться.
- Два новых теста проверяют воспроизводимость/границы и выполнение вставки
  с восстановлением состояния. Проверка оригинальных ZIP, PAC, PS, NV и
  извлечённых ресурсов — PASS.
